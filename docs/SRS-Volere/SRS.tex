\section{Purpose of the Project}


\subsection{User Business}
Tandem is intended for people who build or run applications that use more
than one large language model (LLM). For example, a customer-support chatbot might send
simple questions to a smaller model and harder questions to a more capable
model. Choosing a model based on the meaning or needs of a request is called
\emph{semantic routing}. In the planned deployment, vLLM Semantic Router
selects the target model and routes the request to its inference backend.
It is a routing component in the vLLM ecosystem, separate from the backend's
prefill and decoding execution \hyperref[src:VSR]{[VSR]}.

Using a trained model to produce an answer is called \emph{inference}.
During \emph{prefill}, the model processes the input prompt, including the
conversation history. During \emph{decoding}, it generates the response one
token at a time. When a conversation switches models, the newly selected
model may need to repeat prefill for history that an earlier model has
already processed. This adds response latency and uses GPU compute.

Tandem aims to reduce this repeated prefill through \emph{cross-model
key-value (KV) cache reuse}. A KV cache stores the key and value tensors
produced by the model's attention layers for tokens already processed.
These tensors let the model reuse attention state instead of calculating it
again. Tandem will integrate a compatible cache prepared for the selected
target model into the serving engine, then prefill the remaining prompt and
continue decoding. A source model's KV cache is not assumed to work directly
in a different model; the transfer method and model pair must pass the
compatibility and output tests. If reuse is unavailable, the engine uses its
\emph{native prefill} path, meaning its normal prompt processing.
The initial project runs on one GPU-equipped server and is used by other
software through an application programming interface (API).

\subsection{Goals of the Project}
Tandem aims to make applications that switch between language models cheaper
and faster to run. Building on the model-switching scope in the problem
statement~\hyperref[src:PS]{[PS]}, the project has four main goals:
\begin{description}
\item[G1: Reuse prefill through a KV cache.] Use compatible cross-model KV
cache reuse to preserve prefill work for the shared conversation prefix,
the history at the start of the prompt. This lets the target model avoid
prefilling that prefix again. Reuse is limited to supported model pairs with
a KV cache prepared for the target model.
\item[G2: Reduce inference compute and serving cost.] Avoid repeated prefill to
reduce the GPU computation needed per completed request. Aim to lower the GPU
time and cost needed to serve the same workload, counting the work needed to
prepare, validate and transfer the KV cache.
\item[G3: Make switching to cheaper models worthwhile.] Help an application
benefit from using a lower-cost model when it is suitable for the task, without
repeated processing of the conversation history using up those savings.
Semantic routing selects the model; Tandem reduces the repeated prefill
caused by the switch.
\item[G4: Lower TTFT and increase throughput.] Reduce \emph{time to first
token (TTFT)}, the wait before the selected model starts returning its answer.
Use the saved computing capacity to increase \emph{throughput}, measured as
completed requests per second on the same hardware, while keeping response
latency within the agreed limits.
\end{description}
For example, a chatbot could use a larger model for a difficult question and
switch to a cheaper model for a simple follow-up. Tandem aims to reuse a
compatible KV cache for the shared history so the cheaper model does not
have to prefill it all again.

Tests will compare the same requests and model choices with and without
Tandem. They will report repeated prompt work, GPU time per completed request,
TTFT, end-to-end latency and throughput. Estimated money savings must state the rates
and assumptions used. Any separate savings attributed to choosing a cheaper
model must identify the alternative model choices being compared.

Correct output, privacy and normal processing when reuse is unavailable remain
required conditions for achieving these goals. Supporting more models,
handling more conversation branches and reducing peak GPU memory use are
possible extensions after the core work succeeds.

\section{Stakeholders}


\subsection{Client}
A potential client is a software company building an application that uses
several language models. Cursor, whose AI development tools support multiple
models, is the organizational example used in the personas below
\hyperref[src:CURSOR]{[CURSOR]}. A customer-support chatbot company is another
example. Such a development team could help define useful requirements,
including which model combinations matter and how much delay users will accept.

In this SRS, the \emph{client} is the organization whose application needs
help guide Tandem's features. A university research lab developing a similar
assistant is another potential client. These are examples of organizations
that could benefit from the project; a current contract is not required.

\subsection{Customer}
A potential customer is an AI hosting provider that runs large language models
for other software teams. Together AI, which offers dedicated model inference,
is the organizational example used in the personas below
\hyperref[src:TOGETHER]{[TOGETHER]}. Another is a company's internal AI
infrastructure team. An organization operating a compatible inference engine
could adopt Tandem to reduce repeated prefill after a router switches models
and handle more requests with its available GPUs.

Here, the \emph{customer} is the person or organization that would adopt and
operate Tandem. The client and customer may be the same organization: a software
company could both build the chatbot and run its model servers. Since Tandem
is planned as an open-source project, adoption does not require buying a licence.

\subsection{Other Stakeholders}
Other people who could benefit include:
\begin{itemize}
\item \textbf{Independent application developers looking to host local LLM:} could provide faster
AI features without needing to build their own serving optimization.
\item \textbf{Inference Data Center Operators:} could make better use of limited GPU capacity
and see clear information about cache reuse and failures.
\item \textbf{Researchers:} could use the test tools and results to study
when sharing cached calculations is useful and when it is ineffective.
\end{itemize}

\subsection{Hands-On Users of the Project}
Tandem is intended to be integrated into an LLM inference engine such as
vLLM. Its users include inference-engine developers who maintain the
integration, infrastructure operators who deploy it, researchers who evaluate
it, and application developers who use the hosting system. The personas in
the next subsection represent these roles: Alex Morgan, Together AI's
inference operations team, Sofia Nguyen and Cursor's application team,
respectively.

Engine developers work with KV cache validation and loading. Operators
configure supported model pairs, enable or disable reuse, monitor GPU resources
and investigate errors. Researchers compare the same workloads with and
without Tandem. Application developers submit requests through the hosting
inference system's existing API or programmatic interface; they do not need
a separate Tandem API. Model selection remains the responsibility of the
configured router, with vLLM Semantic Router used in the planned deployment.

Operators and researchers need basic Linux skills and familiarity with model
serving and GPU resource limits. Developers modifying the integration also
need knowledge of the engine and KV cache handling. People chatting with an
application benefit indirectly and do not need to understand or operate Tandem.

\section{Mandated Constraints}


\subsection{Solution Constraints}
The initial project has these limits:
\begin{description}
\item[C1:] Run text-generation requests on one server.
\item[C2:] Use the target model selected by vLLM Semantic Router, or the same
recorded routing decision when replaying a benchmark.
\item[C3:] Use existing trained models; training the models is outside the project.
\item[C4:] Reuse only an exact matching start of the conversation, using a
model combination and cache-transfer method that have passed the required tests.
\item[C5:] Keep the serving engine's normal prompt processing available
whenever reuse is not possible.
\end{description}
These limits keep the project manageable and allow a fair comparison with the
serving engine running without Tandem~\hyperref[src:PS]{[PS]}.

\subsection{Implementation Environment of the Current System}
Tandem will run on a Linux server with a supported GPU and enough memory
for the models being tested. The Development Plan proposes vLLM as the main
serving engine, with SGLang as an alternative if needed~\hyperref[src:DP]{[DP]}.
A serving engine is the software that loads models, schedules requests and
produces their responses.

Before testing, the team will record the exact engine, model, tokenizer,
GPU software and calculation settings. This list is called the
\emph{configuration record}. Small tests may run on a CPU during development,
but GPU tests are needed to measure serving speed. The model pair for the
first cache-reuse test has not yet been chosen.

\subsection{Partner or Collaborative Applications}
In the planned vLLM deployment, the application sends the conversation messages
and generation parameters, such as temperature and maximum output length.
vLLM Semantic Router selects the target LLM and routes the inference request
to the backend serving that model \hyperref[src:VSR]{[VSR]}.
The target model is the router's decision, rather than a new choice made by
Tandem.

For Tandem's engine integration, the logical inputs are the routed inference
request and, when available, a reference to the previous model's
\emph{source KV cache}. The cache stores attention state for the conversation
prefix it covers. Cache metadata identifies the source model, target model,
cached prefix and token positions. The KV tensors can remain in managed
memory and be accessed through a cache handle or transfer mechanism; they
need not be embedded in the application's HTTP request. This distinguishes
Tandem's internal cache interface from the normal model-serving API
\hyperref[src:VLLMAPI]{[VLLMAPI]}.

The cache-transfer component uses the selected method to prepare a candidate
KV cache for the target model. Tandem validates it, loads an accepted cache
into the target model's KV memory, prefills the \emph{uncached prompt suffix},
then continues autoregressive decoding. The suffix is every prompt token
after the cached prefix. It includes the new user message and may include
earlier messages or formatting tokens that the cache does not cover.
A source model's raw KV tensors are not automatically compatible with another
model. The transfer method and supported model pairs remain decisions for
the proof of concept (OI1).

The complete logical prompt, comprising conversation history and the new
turn, remains available as text or token IDs for prefix validation and native
prefill if reuse fails. Retaining this prompt does not mean recomputing its
cached prefix when reuse succeeds. The cache-transfer component can be part
of the engine integration; it does not require a separate external service.
Benchmark scripts replay the same requests and routing decisions with and
without Tandem. The application manages conversation storage and user access.

\subsection{Off-the-Shelf Software}
The project plans to reuse an existing serving engine, Python, PyTorch,
Hugging Face Transformers, model tokenizers and the GPU software described in
the Development Plan. Their versions and licences will be recorded with each
release. An update to one of these dependencies may require new compatibility
tests. The project does not require training a base model or inventing a new
method for predicting one model's cache from another.

\subsection{Anticipated Workplace Environment}
Team members can develop on their own computers and connect to a Linux
server for GPU work. The Development Plan describes the intended department
GPU resources. Performance tests need a recorded hardware setup and a record
of other work using the same GPU. Short experiments on an available GPU can
help development, but final comparisons need repeatable conditions.

\subsection{Schedule Constraints}
The Development Plan lists the SRS and Hazard Analysis for October 19, 2026,
a proof-of-concept demonstration in November, an initial demonstration in
February, and a final demonstration in late March. Final documentation and
EXPO work follow. The team must check current course announcements for exact
submission dates.

Section~\ref{sec:phases} describes what should be completed at each stage.
The technical tasks in the older Development Plan need updating to match the
current focus on switching between models.

\subsection{Budget Constraints}
The project plans to use existing university GPU resources rather than
purchase new hardware or depend on paid model APIs. The available GPU time
and storage allowance still need to be confirmed. If the available resources
cannot run a planned test, the team will change or reschedule that test and
record the reason.

\subsection{Enterprise Constraints}
Project work is stored in the repository and reviewed through issues and
pull requests. Shared test data must be public, synthetic or used with
permission. Credentials and private conversations must stay out of public
files. Each release records the code and dependency versions used.

\section{Relevant Facts And Assumptions}


\subsection{Relevant Facts}
F1: Tandem's current goal is to reduce repeated prompt processing when a
conversation switches models~\hyperref[src:PS]{[PS]}.
F2: vLLM already supports reusing previously processed shared prompt prefixes;
this reduces prefill work rather than the work of generating new tokens~\hyperref[src:APC]{[APC]}.
F3: A cache must match the intended model, conversation and calculation settings.
Having the same size is not enough to show it can be reused correctly.
F4: Repeating model results requires controlled software and hardware settings~\hyperref[src:REPRO]{[REPRO]}.
The supplied project files do not yet contain measured Tandem performance or
proof that a chosen cross-model cache works.

\subsection{Business Rules}
BR1: Tandem uses the router-selected target model. In the planned deployment,
vLLM Semantic Router makes that selection; benchmark replay preserves it.
BR2: A valid request can still run normally when no cache can be reused.
BR3: Cached private information is shared only with requests allowed to use it.
BR4: Responses, errors and measurements keep the correct request ID.
BR5: A performance claim includes the test requests, settings and output checks
needed to assess it.
BR6: A model/cache setup is listed as supported only after it passes the required tests.

\subsection{Assumptions}
A1: The server operator controls the model files and settings. The initial
cache provider runs in this trusted environment; users cannot upload arbitrary
cache files directly.
A2: The application supplies the intended conversation history and new turn;
vLLM Semantic Router supplies the target-model selection. Tandem still checks
that the request is well formed and within supported limits.
A3: The available server can run the selected models normally. Tests still cover
what happens when memory runs out.
A4: The team can find at least one useful model pair and cache-transfer method.
This is a question for the proof of concept, not an established result.
A5: Public or synthetic text is available for repeatable tests.
A6: The team can control or record other work using the GPU during testing.
If an assumption is wrong, the team will review the affected requirements and
record any change to the test plan.

\section{The Scope of the Work}


\subsection{The Current Situation}
A conversation application saves the history and includes it with later
requests. If vLLM Semantic Router selects a different model for the next turn, that model may
need to process the history again. The serving engine may already have useful
prefix-cache features, and those features stay enabled in the comparison.
Tandem investigates whether a cache prepared for the new model can reduce
additional repeated work while preserving its response.

\subsection{The Context of the Work}
\begin{tabularx}{\textwidth}{@{}lX@{}}
\toprule Outside system or user & Information exchanged with Tandem\\\midrule
Application & Supplies conversation messages, request ID and generation settings. Receives output tokens and completion or error status.\\
Semantic router & Selects the target model and routes the inference request. The planned deployment uses vLLM Semantic Router.\\
Cache component & Makes source KV state available by reference and prepares a candidate target-model cache with compatibility and prefix metadata.\\
Server operator & Supplies supported settings and resource limits. Receives status information and error messages.\\
Test driver & Sends repeatable requests at recorded times. Receives individual and summary measurements.\\
\bottomrule
\end{tabularx}
Inside Tandem's scope are request validation, KV cache compatibility checks,
loading an accepted KV cache, prefilling the remaining prompt, decoding,
native-prefill fallback and result reporting. The
test tools also compare runs with and without Tandem. Selecting the model and
inventing a new cache-prediction method remain outside the project.

\subsection{Work Partitioning}
BE1: A request arrives. Check its inputs and find the selected model.
BE2: A possible cache is available. Check it, then reuse it or process the
prompt normally.
BE3: The model produces a token. Return it with the correct request ID.
BE4: A request finishes, fails, times out or is cancelled. Report its final
status and release memory that no active request still needs.
BE5: A test run starts. Send the same requests with and without Tandem and
record the comparison.
BE6: A configuration changes. Check the new settings and stop using cached
state that no longer matches them.

\subsection{Specifying a Business Use Case (BUC)}
\textbf{BUC1: Answer the next conversation message.} The application has a
new message, and vLLM Semantic Router selects the target model. If a compatible
KV cache can be prepared for the shared prefix, Tandem loads it and prefills
only the uncached suffix. Otherwise, the model
processes the prompt normally. The application receives the response under
the same request ID. Invalid inputs are rejected clearly, and a failure during
processing is reported rather than presented as a successful answer.

\textbf{BUC2: Check whether a setup benefits from Tandem.} An operator or
researcher runs a fixed set of requests with and without the changes. The
report compares output consistency, response times, completed requests,
resource use and failures. It states which models and settings were tested.

\section{Business Data Model and Data Dictionary}


\subsection{Business Data Model}
A test run has a configuration record and a list of requests with arrival
times. Each request has a unique ID, a router-selected model, an allowed
sharing group and possibly a source KV cache reference and candidate
target-model caches to consider. Each cache records where it came
from, which model it is prepared for and which history it represents.

Output events and measurements refer back to the request ID. Each accepted
request has one final result: completed, failed or cancelled. Rejected requests
are recorded separately. Comparisons match the same logical request across
the normal run and the Tandem run. The application, not Tandem, stores the
long-term conversation history.

\subsection{Data Dictionary}
The fields below describe the logical inference inputs and engine-side cache
state. They do not require the application to send KV tensors in an HTTP
payload. The uncached suffix is derived after validating the cached prefix;
the full prompt remains available for validation and fallback.

An unusable optional cache normally leads to standard prompt processing;
invalid requests or server failures can still prevent a response. Normal logs
and measurement files do not include the raw conversation or cache contents.

\section{The Scope of the Product}


\subsection{Product Boundary}
Tandem covers text generation, exact checks for shared conversation history,
use of tested caches, separation of requests, return to normal processing and
repeatable evaluation on one server. The application supplies the conversation
and generation settings; the operator configures the available models.
vLLM Semantic Router selects the target model. The trusted engine-side cache
component supplies source KV state and prepares candidate target-model caches.
The baseline keeps the serving engine's existing prefix-cache features.

The project does not include training base models, inventing a new cache
predictor, building the router, retrieving documents, coordinating agents,
building a graphical application or running across several servers. Similar
meaning is not enough for reuse: the covered start of the tokenized history
must match exactly. Supported models and settings are listed explicitly.

\subsection{Product Use Case Table}

\toprule ID & What happens & Required result\\\midrule\endhead
PUC1 & A valid request has a usable cache & Reuse the matching history and generate with the chosen model.\\
PUC2 & A cache is missing or fails a check & Process the prompt normally and record why reuse was not used.\\
PUC3 & Reuse fails during processing & Restart safely before output where possible; otherwise report the failure.\\
PUC4 & An operator changes settings & Accept supported settings and reject inconsistent or unsupported ones.\\
PUC5 & A researcher starts a comparison & Run matching requests with and without Tandem and produce a repeatable report.\\

\bottomrule
\end{longtable}

\subsection{Individual Product Use Cases (PUC's)}
\textbf{PUC1: Reuse available history.} Check the request and selected model.
Compare the possible cache with the exact history, model setup and sharing
permissions. If every check passes and memory is available, load the cache,
process the remaining prompt and return output in order with the request ID.

\textbf{PUC2: Process without reuse.} If no cache is available or a check
fails, record the reason and use the selected model's normal processing.
This is expected behaviour, not a rejection of an otherwise valid request.
Normal same-model prefix caching remains available.

\textbf{PUC3: Handle a reuse failure.} If no output has been returned,
discard invalid state and attempt a limited restart through normal processing.
If output has already started, end the response with a failure status. Do not
append a newly restarted answer to the partial answer.

\textbf{PUC4: Change the setup.} Check the new configuration before using it
for new requests. Keep untested model/cache combinations disabled. Do not reuse
old state when its model or configuration version no longer matches.

\textbf{PUC5: Compare performance.} Record the settings and test requests,
check output consistency, then run repeated paired comparisons. Include failed
requests in the report. A setup that fails output checks is not approved for reuse.

\textbf{PUC6: Stop a request.} Record cancellation or timeout and release
the request's claim on memory. Keep any shared state still needed by another
active request intact.

\section{Functional Requirements}


\subsection{Functional Requirements}
\label{sec:functional}
These requirements describe what Tandem and its test tools must do. ``Shall''
marks a required behaviour. The \emph{fit criterion} explains how that
requirement will be checked. The source and rationale explain why it is needed.
Names beginning with T- identify planned tests, not tests already completed.

\par\medskip\noindent\phantomsection\label{req:FR-01}
\textbf{FR-01 --- Check requests before processing}\par
Tandem shall check each request against the Data Dictionary before accepting it.\par
\textbf{Fit criterion.} T-ADM sends missing fields, unknown models, invalid settings, repeated request IDs and prompts that exceed the limits. Each is rejected with a clear reason before generation begins. A valid request without a cache is accepted.\par
\textbf{Source and rationale.} BR1, BR2; a bad request and an unavailable cache are different situations.



\par\medskip\noindent\phantomsection\label{req:FR-02}
\textbf{FR-02 --- Use the requested model and inputs}\par
Tandem shall use the router-selected model version, complete ordered prompt and accepted generation settings.\par
\textbf{Fit criterion.} T-SEM compares the model version, formatted prompt and applied settings with the same request run normally. No history or instruction is left out.\par
\textbf{Source and rationale.} BR1; an optimization must not change what the application asked the model to do.



\par\medskip\noindent\phantomsection\label{req:FR-03}
\textbf{FR-03 --- Match the shared history exactly}\par
Tandem shall reuse only an exact matching start of the history after formatting and tokenizing it for the selected model.\par
\textbf{Fit criterion.} T-MATCH changes a message, message order, system instruction, tokenizer or conversation-format version, or token position. Each relevant mismatch prevents that cache from being used. The latest user turn is still processed as new input.\par
\textbf{Source and rationale.} C4; similar meaning or equal cache sizes do not establish an exact match.



\par\medskip\noindent\phantomsection\label{req:FR-04}
\textbf{FR-04 --- Validate a KV cache before reuse}\par
Tandem shall use a candidate KV cache only when all compatibility, prefix-matching, permission, readiness and resource checks in Section~\ref{sec:formal} pass.\par
\textbf{Fit criterion.} T-COMP makes each check fail separately, then tests a valid case. A failed or unknown check prevents reuse. A ready, tested, permitted, matching cache with available resources can be used.\par
\textbf{Source and rationale.} G1, C4, BR3, BR6; the cache must be suitable for this request, not merely available.



\par\medskip\noindent\phantomsection\label{req:FR-05}
\textbf{FR-05 --- Load the KV cache and prefill the remaining prompt}\par
Tandem shall load an accepted KV cache into the serving engine for the selected target model, prefill the remaining prompt once in its original order, and continue decoding from that state.\par
\textbf{Fit criterion.} T-REUSE checks the cached history, remaining-token positions and measured prompt work for a tested setup. Output checks meet \hyperref[req:NFR-05]{\texttt{NFR-05}}.\par
\textbf{Source and rationale.} G1; the work is to integrate compatible cross-model KV cache reuse into the serving engine.



\par\medskip\noindent\phantomsection\label{req:FR-06}
\textbf{FR-06 --- Keep normal processing available}\par
Tandem shall use normal model processing when reuse is off, unavailable or unsuitable, while keeping the engine's existing prefix-cache features.\par
\textbf{Fit criterion.} T-NATIVE checks same-model requests, requests without shared history, missing caches and unsupported model pairs. They still use the correct model and meet the normal output rules.\par
\textbf{Source and rationale.} C5, BR2; a valid request must not fail solely because Tandem cannot speed it up.



\par\medskip\noindent\phantomsection\label{req:FR-07}
\textbf{FR-07 --- Recover from or report a reuse failure}\par
Tandem shall follow the restart and failure rules in Section~\ref{sec:formal} if a cache-reuse attempt fails.\par
\textbf{Fit criterion.} T-FAIL forces cache-loading failures before and after output begins. Before output, a restart uses valid normal-processing state at most \texttt{RECOVERY\_LIMIT} times. Otherwise, a failure is reported.\par
\textbf{Source and rationale.} BR2, BR4; repeated retries or mixing two answers would hide what happened.



\par\medskip\noindent\phantomsection\label{req:FR-08}
\textbf{FR-08 --- Keep output attached to the right request}\par
Tandem shall return output in order with the correct request ID and record exactly one final status for each accepted request.\par
\textbf{Fit criterion.} T-STATE runs overlapping requests, cancellations and failures. Output order remains correct, and each accepted request ends as completed, failed or cancelled. Rejected requests have separate records.\par
\textbf{Source and rationale.} BR4; simultaneous requests and restarts must not duplicate or mix responses.



\par\medskip\noindent\phantomsection\label{req:FR-09}
\textbf{FR-09 --- Release memory when a request ends}\par
Tandem shall release resources held for a completed, failed or cancelled request without removing shared state another active request still needs.\par
\textbf{Fit criterion.} T-LIFE repeats these cases for \texttt{LIFECYCLE\_CYCLES}. No finished request retains its own allocation, and other active requests keep producing correct results. The engine may retain reusable cache data under its normal policy.\par
\textbf{Source and rationale.} G2, G4; unused request allocations are different from caches intentionally kept for reuse.



\par\medskip\noindent\phantomsection\label{req:FR-10}
\textbf{FR-10 --- Record what happened for each request}\par
Tandem shall record the run and request IDs, selected model, final status, reuse decision and reason, timings, and actual prompt-token work in a structured result.\par
\textbf{Fit criterion.} T-METRIC checks the result format and compares measured counts with a short known prompt. An unavailable measurement is marked missing with a reason rather than replaced by an estimate.\par
\textbf{Source and rationale.} G1--G4; users need to see both the saved work and the failures.



\par\medskip\noindent\phantomsection\label{req:FR-11}
\textbf{FR-11 --- Use matching requests for comparisons}\par
The test tools shall run the same requests, model choices, arrival times and response settings with and without Tandem.\par
\textbf{Fit criterion.} T-EVAL compares request contents and configuration records. Unexplained differences invalidate the comparison. Existing prefix caching remains enabled whenever it is enabled in the baseline.\par
\textbf{Source and rationale.} G1--G4, BR5; weakening the comparison system would give a misleading benefit.



\par\medskip\noindent\phantomsection\label{req:FR-12}
\textbf{FR-12 --- Make comparison results repeatable}\par
The test tools shall report response times, completed requests per second, prompt work, total allocated GPU time and GPU time per completed request, output differences, fallback results and settings for individual cases and the overall run. Any estimated serving cost shall include its rates and calculation.\par
\textbf{Fit criterion.} T-REPORT checks that another evaluator can find the code and library versions, hardware, model versions, random seeds, test requests, repetition counts, starting cache conditions and failures needed to repeat the test. The report includes cache-preparation and transfer overhead. Cost estimates follow the method in the Costs section; if no price is supplied, it reports GPU time without claiming money savings.\par
\textbf{Source and rationale.} G1--G4; a speed result needs enough information to be checked independently.



\par\medskip\noindent\phantomsection\label{req:FR-13}
\textbf{FR-13 --- Control supported cache-reuse setups}\par
Tandem shall check its settings, provide a reuse on/off control and keep a versioned list of tested model/cache setups.\par
\textbf{Fit criterion.} T-CONFIG rejects inconsistent settings, uses normal processing for untested combinations, and prevents incompatible old caches from being used after a model or configuration change.\par
\textbf{Source and rationale.} C4, C5; loading a model successfully does not show that cache reuse works for it.



\par\medskip\noindent\phantomsection\label{req:FR-14}
\textbf{FR-14 --- Test a setup before enabling reuse}\par
The test tools shall keep passing output, privacy and failure-handling results for each model/cache setup enabled for cross-model reuse.\par
\textbf{Fit criterion.} T-QUAL tries to enable a setup with missing or failed evidence; reuse stays off. A passing record lists the settings and limits that were actually tested.\par
\textbf{Source and rationale.} C4, BR6, A4; the chosen transfer approach must work correctly before its speed is accepted.



\par\medskip\noindent\phantomsection\label{req:FR-15}
\textbf{FR-15 --- Stop cancelled or timed-out requests}\par
Tandem shall accept cancellation and enforce the configured time limit for an accepted request.\par
\textbf{Fit criterion.} T-CANCEL stops queued and running requests and lets a request exceed \texttt{REQUEST\_TIMEOUT}. Each ends with the right reason at a point the engine can safely stop, and releases resources under \hyperref[req:FR-09]{\texttt{FR-09}}.\par
\textbf{Source and rationale.} G2, G4; an ongoing GPU operation may need to reach a safe stopping point first.


\par\medskip\noindent\textbf{Formal specification of cache reuse and failure behaviour.}
\label{sec:formal}
These rules state exactly when a cache may be used and what happens if reuse
fails. They are written mathematically because a mistake here could produce
an incorrect response or use another request's private history. The equations
make the prose requirements precise; they do not prescribe the internal code.

For example, if a conversation moves from Model A to Model B, Tandem must
check that the proposed cache is prepared for the tested Model B setup, covers
the exact required history and is permitted for this request. If any check
fails, Model B processes the prompt normally.

In the equations, $r$ is a request, $c$ is a possible cache, $C$ is the set
of caches supplied for consideration, and $M$ is the list of tested model/cache
setups. $m(r)$ is the chosen model version and $d(r)$ is
the request's allowed sharing group. $P(r)$ is the complete prompt after the
chosen model's formatting and tokenization. $H(r)$ is its history portion,
without the new turn. $K(c)$ is the token sequence represented by the cache,
and $n(c)=|K(c)|$ is its length. A tested setup records the model versions,
transfer method, tokenizer, conversation format, positions, numeric precision,
cache format and engine settings required by
\hyperref[req:FR-14]{\texttt{FR-14}}.

Each check below is either true or false. Missing information makes the check
false, so incomplete information cannot permit reuse.
\begin{description}
\item[$V(r)$:] The request has valid inputs and fits the selected model's limits.
\item[$Q(c,r)$:] The model/cache setup is in the tested list $M$, and this
request falls within the limits covered by those tests.
\item[$I(c,r)$:] The cache covers a nonempty start of the history:
$0<n(c)\leq |H(r)|$ and $K(c)=P(r)[1:n(c)]$. Its formatting, tokenizer and
token positions also match.
\item[$A(c,r)$:] The application permits this request to use the cached
history. Another request's private instructions or answer are not included.
\item[$D(c)$:] The cache is complete, ready, valid and still belongs to the
current configuration version.
\item[$B(c,r)$:] Enough usable resources can be reserved without changing
cache data that another active request still needs.
\end{description}
\[
 E(c,r) \equiv V(r)\land Q(c,r)\land I(c,r)\land A(c,r)\land D(c)\land B(c,r).
\]
$E(c,r)$ is true only when \emph{all} of these checks pass. Let $u$ mean
that the operator has turned cache reuse on. The initial choice is:
\[
\operatorname{path}(r)=
\begin{cases}
\text{reject}, & \neg V(r),\\
\text{reuse }c, & V(r)\land u\land\exists c\in C:E(c,r),\\
\text{normal processing}, & V(r)\land(\neg u\lor\neg\exists c\in C:E(c,r)).
\end{cases}
\]
In words: reject an invalid request; try reuse only when it is enabled and
there is an acceptable cache; otherwise use normal processing. If several
caches pass, choosing one must still satisfy every check.

The cache covers $P(r)[1:n(c)]$. The model processes the remaining prompt,
$P(r)[n(c)+1:|P(r)|]$, in order. No prompt token is skipped or logically
processed twice. Matching cache sizes without the model and history checks
is not enough.

After a request is accepted, it is prepared, generates output and ends. If reuse
fails before any output is returned, Tandem may restart normal processing at
most \texttt{RECOVERY\_LIMIT} times. If a safe restart is not possible, report
failure. If output has already started, report failure without appending a new
answer. Cancellation or timeout also ends the request with the correct reason.
Each accepted request has exactly one final status:
\[
 \operatorname{terminal}(r)\in\{\text{completed},\text{failed},\text{cancelled}\}.
\]

For output checks, $z_T$ and $z_B$ are corresponding scores from the same
selected model with and without Tandem. Both runs are given the same tokens
up to the point being compared. For every finite score $j$, require
\[
 |z_{T,j}-z_{B,j}|\leq\varepsilon_{\mathrm{abs}}
                 +\varepsilon_{\mathrm{rel}}|z_{B,j}|.
\]
Here $\varepsilon_{\mathrm{abs}}=\texttt{SCORE\_ATOL}$ and
$\varepsilon_{\mathrm{rel}}=\texttt{SCORE\_RTOL}$. The first is a fixed small
allowance; the second allows a difference proportional to the reference score.
Unexpected nonfinite values, such as an invalid number, fail the test. Any
normal token-masking rules must be applied consistently before comparison.

Greedy generation must also produce the same token sequence, written
$Y_T=Y_B$, for the specified test length or until both runs stop earlier.
Setting the same random seed does not by itself guarantee that every sampled
answer will match~\hyperref[src:REPRO]{[REPRO]}. Sampling settings need their
own recorded checks before a setup is supported; otherwise the request uses
normal processing.

First, repeat the model run without Tandem to check that the chosen setup is
stable enough for this comparison. Then compare runs with and without reuse.
Passing the tests supports the tested requests and settings; it is not a
mathematical proof that every possible prompt will behave identically.

The minimum test set includes same-model turns and model switches, with and
without shared history. It also includes usable, missing and rejected caches;
cold and warm caches; one request at a time and simultaneous requests; and
forced failure cases. Both sides of a comparison use the same conversations,
model choices, response settings, arrival times and resource limits.
Reports record which cache hits actually occurred and any work required to
prepare the caches. A difference between the setups must be explained.

The starting prompt lengths and request counts are listed in
Section~\ref{sec:constants}. Tests that exceed the model or hardware limits are
skipped with a recorded reason. Each setup has \texttt{WARMUP\_RUNS} practice
runs followed by \texttt{PAIRED\_RUNS} timed pairs. The order alternates so that
one condition does not always run first. Reports include variation, failures,
slowdowns and cases where no useful improvement is found.

Completed requests per second are counted over the period from the first
arrival to the last final status. Failed and cancelled requests stay in the
report and are not counted as successful completions. If a request returns no
token, TTFT is recorded as unavailable with a reason. Full request time runs
from arrival to its final status. Counts of actual prompt work are reported
separately from the length of the shared history. GPU memory use is reported
when measured directly; it is not guessed from the number of avoided tokens.

\section{Look and Feel Requirements}


\subsection{Appearance Requirements}
Tandem does not provide a graphical interface. Users see command-line
messages, logs and test reports. These outputs need clear labels and units.

\par\medskip\noindent\phantomsection\label{req:NFR-01}
\textbf{NFR-01 --- Make results readable}\par
Tandem shall give human-readable results clear field names and units as well as providing structured data for other programs.\par
\textbf{Fit criterion.} T-REPORT checks that a reader can distinguish reused, normal and fallback processing, understand units and identify failures without examining engine internals.\par

\subsection{Style Requirements}

\section{Usability and Humanity Requirements}


\subsection{Ease of Use Requirements}
Developers and operators use the existing serving API for ordinary requests.
The instructions explain any additional setup needed to supply a cache.
Application end users do not need a new interface or knowledge of caching.

\par\medskip\noindent\phantomsection\label{req:NFR-02}
\textbf{NFR-02 --- Make setup instructions usable}\par
A technical user with the listed prerequisites shall be able to install Tandem and run its basic setup example by following the instructions.\par
\textbf{Fit criterion.} T-USABILITY asks a reviewer who did not write the instructions to follow them in a clean supported environment. Every necessary command and expected result must be documented.\par
\textbf{Source and rationale.} Operators need a repeatable setup process.

\subsection{Personalization and Internationalization Requirements}
The first version does not need personalized controls or translated
administrative messages. It must preserve supported text, including Unicode
characters, through the selected model's usual tokenizer and conversation
format. Tandem must not rewrite text to make two histories appear to match.

\par\medskip\noindent\phantomsection\label{req:NFR-03}
\textbf{NFR-03 --- Preserve supported text}\par
Tandem shall preserve valid Unicode input through the selected model's normal conversation formatting and tokenization.\par
\textbf{Fit criterion.} T-TEXT checks accented characters, non-Latin scripts, whitespace and delimiters. The prompt tokens match normal processing, with no extra text changes introduced by Tandem.\par
\textbf{Source and rationale.} C4; text differences must not lead to false history matches.

\subsection{Learning Requirements}
The guide explains what cache reuse does, which setups are supported and
what happens when reuse is unavailable. It includes a simple example that
checks the installation and shows how to read a reuse result. Documentation is
checked through \hyperref[req:DR-01]{\texttt{DR-01}} and
\hyperref[req:NFR-02]{\texttt{NFR-02}}.

\subsection{Understandability and Politeness Requirements}
Messages explain the problem and what the operator can do next. If a cache
cannot be used but the request can still run normally, the message says so.

that has passed reuse tests. Messages identify invalid fields without repeating
private conversation text.

\subsection{Accessibility Requirements}
Commands and reports use readable text and do not depend on colour.
Machine-readable results can be displayed by other tools. There is no graphical
interface to assess in the first version. Instructions should work without
requiring a particular visual editor.

\section{Performance Requirements}


\subsection{Speed and Latency Requirements}
\label{sec:performance}
The main speed measure is how long the application waits for the first output
token. Tests also measure the full request time and completed requests per
second. The test set is chosen before the final comparison and includes cases
where reuse should help and normal requests where it should not be needed.

Timing includes waiting in the queue, checking and preparing a cache, moving
it into the engine, processing the rest of the prompt and generating output.
Both sides of a comparison must handle model loading in the same way. Reports
explain how caches were prepared and include any work needed to create or
transfer them. Failed and cancelled requests remain visible.

For each paired trial, $L_B$ is the median first-token wait without Tandem and
$L_T$ is the same measure with Tandem. $P_B,P_T$ are their p95 waiting times,
and $Q_B,Q_T$ are completed requests per second. We compare them using
\[
 S_L=L_B/L_T,\qquad S_Q=Q_T/Q_B.
\]
A value above one means an improvement. Test T-STAT calculates uncertainty
ranges by repeatedly resampling complete pairs of trials, using the
\texttt{CONFIDENCE} and \texttt{BOOTSTRAP\_DRAWS} settings. Individual requests
from one run are not counted as separate independent runs. This helps avoid
calling random timing changes an improvement.

\par\medskip\noindent\phantomsection\label{req:NFR-04}
\textbf{NFR-04 --- Show a useful reduction in waiting time}\par
On at least one model-switch test chosen in advance, the tested integration shall reduce repeated prompt work and improve median first-token waiting time beyond normal timing variation.\par
\textbf{Fit criterion.} T-PERF requires fewer actually computed prompt tokens and a lower confidence bound for $S_L$ above one. Output checks pass and failures do not increase. Results for other tests, including slowdowns, are reported.\par
\textbf{Source and rationale.} G1, G2, G4; the project must demonstrate a measured benefit rather than assume a fixed speedup.

\subsection{Safety-Critical Requirements}
The prototype is not intended to control a safety-critical system. Relevant
harms still include incorrect responses, disclosure of private information,
unavailable service and wasted resources. The security requirements in
Section~\ref{sec:security} apply even when their checks reduce the possible
speed improvement. The Hazard Analysis will review the risks linked to those
requirements.

\subsection{Precision or Accuracy Requirements}
The question here is whether using Tandem changes the selected model's
response compared with running that same model normally. It is not a test of
whether the model's answer is factually true.

Tests use the same prompt, model version and calculation settings. They compare
the model's next-token scores at the same places in the same text. They also
compare several generated tokens using greedy generation, which always picks
the highest-scoring next token. Comparing two answers that already contain
different earlier tokens would not be a fair score comparison.

\par\medskip\noindent\phantomsection\label{req:NFR-05}
\textbf{NFR-05 --- Keep the selected model's output consistent}\par
Each supported cache-reuse setup shall meet the score-difference and generated-token checks in Section~\ref{sec:formal} for its declared test set.\par
\textbf{Fit criterion.} T-SCORE checks corresponding scores using \texttt{SCORE\_ATOL} and \texttt{SCORE\_RTOL}. T-GEN requires the same greedy tokens for \texttt{CHECK\_TOKENS}, or until both runs stop earlier. A mismatch prevents approval; limits cannot be changed afterwards just to pass.\par
\textbf{Source and rationale.} BR1, BR6; the listed tolerances are proposed values the team still needs to review.

\subsection{Robustness or Fault-Tolerance Requirements}
When an optional cache cannot be used, a valid request should still be able
to run normally. Some problems, such as an unavailable model or an exhausted
GPU, can prevent any response. Those problems need a clear failure status
rather than silent loss of the request.

\par\medskip\noindent\phantomsection\label{req:NFR-06}
\textbf{NFR-06 --- Report failures and allow later normal requests}\par
Tandem shall explain why an accepted request failed and keep normal processing usable after a recoverable cache failure.\par
\textbf{Fit criterion.} T-FAIL supplies incomplete caches, mismatched details, memory-allocation failures and timeouts. Results follow \hyperref[req:FR-07]{\texttt{FR-07}}. If the engine remains healthy, a later valid request can still finish normally. An engine that cannot recover requires operator attention.\par
\textbf{Source and rationale.} C5, BR2; recovery depends on having a working engine and enough resources.

\subsection{Capacity Requirements}
Capacity describes how many requests can run together and how much prompt
text and memory a tested setup can handle. These limits depend on the models
and hardware. Tests must also check what happens when a request exceeds them.
Serving more requests is useful only if response delays remain acceptable.

\par\medskip\noindent\phantomsection\label{req:NFR-07}
\textbf{NFR-07 --- Handle more requests without excessive delay}\par
On at least one shared-history test chosen in advance, Tandem shall improve completed requests per second beyond timing variation while staying within the allowed p95 delay increase.\par
\textbf{Fit criterion.} T-LOAD requires a lower confidence bound for $S_Q$ above one and an upper bound for $P_T/P_B$ no greater than $1+\texttt{REGRESSION\_LIMIT}$, with no extra failed requests. The requests and arrival times are reported.\par
\textbf{Source and rationale.} G2, G4; serving more requests is not useful if the longer waits become unacceptable.



\par\medskip\noindent\phantomsection\label{req:NFR-08}
\textbf{NFR-08 --- Limit slowdowns for normal requests}\par
For tests that do not need Tandem's cache reuse, the integration shall stay within the allowed changes to response time and throughput.\par
\textbf{Fit criterion.} T-NATIVE-PERF requires upper bounds for $L_T/L_B$ and $P_T/P_B$ at most $1+\texttt{REGRESSION\_LIMIT}$ and a lower bound for $Q_T/Q_B$ at least $1-\texttt{REGRESSION\_LIMIT}$. If the uncertainty is too large, the result is inconclusive, not a pass.\par
\textbf{Source and rationale.} G4, C5; the extra checks and bookkeeping must not cause excessive overhead.

\subsection{Scalability or Extensibility Requirements}
The first version supports one server and a recorded set of tested model
combinations. More model pairs, GPU types and conversation branches can be
added later. Coordinating several servers and guaranteeing proportional
speedups as hardware is added are outside the initial scope.

\par\medskip\noindent\phantomsection\label{req:NFR-09}
\textbf{NFR-09 --- Publish supported models and limits}\par
Each release shall list the model/cache setups that passed testing, their simultaneous-request and token limits, and unsupported settings.\par
\textbf{Fit criterion.} T-QUAL checks supported limit values and values just beyond them. Each support claim has test results. Untested setups remain experimental or have reuse disabled.\par
\textbf{Source and rationale.} C4, BR6; users need to know what has actually been checked.

\subsection{Longevity Requirements}
The team plans to maintain the project through the final capstone release.
Each release keeps the code version, dependency versions, test setup and results
needed to repeat its checks. A future model or serving-engine update must be
tested before it is listed as supported.

\section{Operational and Environmental Requirements}


\subsection{Expected Physical Environment}
Tandem runs on a normally maintained laboratory or server-room computer.
The host organization supplies power, cooling, storage and hardware maintenance.
No extra sensors or physical equipment are required. Tandem reports hardware
or system failures that the serving engine can detect.

\subsection{Wider Environment Requirements}
The main test environment is Linux with the selected GPU software and model
files. Small correctness checks may also run on a development computer. Those
small tests do not establish how fast the GPU server will run.

\par\medskip\noindent\phantomsection\label{req:NFR-10}
\textbf{NFR-10 --- Record how to recreate the test setup}\par
Each tested release shall provide the software/hardware record and commands needed to recreate its declared software setup on compatible hardware.\par
\textbf{Fit criterion.} T-REPRO rebuilds the setup and runs the basic and output tests. Model and dependency versions and build settings can be identified. Any hardware or competing-load differences are reported when repeating speed tests.\par
\textbf{Source and rationale.} C1, BR5, BR6; the setup can affect both speed and numerical output.

\subsection{Requirements for Interfacing with Adjacent Systems}
The Data Dictionary and
\hyperref[req:FR-01]{\texttt{FR-01}}--\hyperref[req:FR-08]{\texttt{FR-08}}
define the logical inputs and outputs. vLLM Semantic Router supplies the
target-model decision. The engine-side cache interface supplies the source
cache handle, prepared candidate cache and compatibility metadata; the
uncached suffix is derived from the validated prefix. Supported generation
settings are listed by version. The host
application checks user identity and assigns sharing permissions.

\subsection{Productization Requirements}
A developer should be able to install the prototype from the repository,
set up the documented models and run a simple example with reuse turned off.
Reuse can then be enabled for a setup that has passed its tests. Model files
are obtained through permitted distribution channels. The initial deliverable
is an installable prototype; hosting a commercial online service is outside scope.

\subsection{Release Requirements}
Each release includes its code version, software requirements, supported
model setups, known limitations and test results. Source and documents are
available in the repository. A setup that fails a required test stays labelled
experimental or has reuse disabled. A release cannot claim a performance goal or
correctness requirement was met when its recorded tests show otherwise.

\section{Maintainability and Support Requirements}


\subsection{Maintenance Requirements}
Maintainers will need to add tested model combinations and respond to
serving-engine updates. A routine setup change should not force application
developers to change how they submit requests.

\par\medskip\noindent\phantomsection\label{req:NFR-11}
\textbf{NFR-11 --- Add a setup without changing application inputs}\par
For an already supported transfer method, a maintainer shall be able to add a model/cache setup through documented settings or integration changes without changing application request fields or normal fallback behaviour.\par
\textbf{Fit criterion.} T-MAINT follows one example extension and verifies that existing API and normal-processing tests still pass without changes to those tests. A completely new transfer method is outside this routine change.\par
\textbf{Source and rationale.} Maintainers should not force application developers to rewrite requests for a new setup.

\subsection{Supportability Requirements}
Users report problems through repository issues. A useful report includes
the model/software versions, error code, steps to repeat the problem and a
non-private example. The capstone does not promise a support response time.

\par\medskip\noindent\phantomsection\label{req:NFR-12}
\textbf{NFR-12 --- Explain status and error codes}\par
The release shall explain every documented rejection, fallback and failure code and state what the operator should do, including when no action is needed.\par
\textbf{Fit criterion.} T-DIAG compares the code list with deliberately triggered outcomes. Messages identify the setup sufficiently to repeat the problem while meeting \hyperref[req:SR-06]{\texttt{SR-06}}.\par
\textbf{Source and rationale.} BR2, BR4; an unused cache must be distinguishable from a failed request.

\subsection{Adaptability Requirements}
A new model version, GPU or software combination must pass the relevant
tests before reuse is enabled. The cache connection should be documented so
that another provider or serving engine can be considered later. The first
release does not have to support a second serving engine.

\par\medskip\noindent\textbf{Likely and unlikely changes.}
LC1: More model pairs and versions are likely to be added; their settings and
tests should be easy to update.
LC2: Serving engines may change their cache formats or interfaces; the code
that connects Tandem to them should be identifiable and documented.
LC3: Test requests and available hardware may change; test records should make
those differences clear.
LC4: The team may revise proposed test limits before approving the final plan;
values and reasons belong in the settings table.

UC1: Training base models and choosing the model for a request are expected to
remain outside Tandem.
UC2: The initial version is expected to remain a single-server project.
UC3: Reuse is expected to require exact text-token matches and sharing permission,
rather than accepting text merely because it has a similar meaning.

\section{Security Requirements}


\subsection{Access Requirements}
\label{sec:security}
The first version works within a server environment controlled by its
operator. The application and cache provider are trusted parts of that setup.
The host is responsible for accounts and network access; Tandem still checks
whether the current request is allowed to use the proposed cached history.

\par\medskip\noindent\phantomsection\label{req:SR-01}
\textbf{SR-01 --- Allow only permitted history sharing}\par
Tandem shall reuse cached history only when the host application permits the current request to use it.\par
\textbf{Fit criterion.} T-ISOLATION sends matching histories under different sharing groups and tries to change permission through request-controlled data. Unauthorized caches are neither used nor exposed.\par
\textbf{Source and rationale.} BR3; addresses risk H2.

\subsection{Integrity Requirements}
Before using a cache, Tandem needs to know that it is complete, matches the
current settings and belongs to a model/cache setup that has passed its tests.
Finding a cache in memory is not enough.

\par\medskip\noindent\phantomsection\label{req:SR-02}
\textbf{SR-02 --- Do not use incomplete or incompatible caches}\par
Tandem shall not reuse a cache that is incomplete, has inconsistent details, belongs to an outdated setup, has an unsupported source, or failed the required tests.\par
\textbf{Fit criterion.} T-COMP changes each condition separately. The request uses normal processing or receives a clear server/resource failure; the rejected cache never enters generation. Missing test evidence counts as unsupported.\par
\textbf{Source and rationale.} C4, BR6; addresses risks H1 and H3.



\par\medskip\noindent\phantomsection\label{req:SR-03}
\textbf{SR-03 --- Protect caches still in use}\par
Tandem shall prevent a cache needed by an active request from being removed, changed or reassigned in a way that invalidates that request.\par
\textbf{Fit criterion.} T-LIFE overlaps generation, cancellation and cache replacement/removal. Active output meets \hyperref[req:NFR-05]{\texttt{NFR-05}}, and finished requests release resources under \hyperref[req:FR-09]{\texttt{FR-09}}.\par
\textbf{Source and rationale.} G2, G4; addresses risk H4.

\subsection{Privacy Requirements}
Conversation history and the calculations derived from it can contain private
information. A request may use shared history only when permitted, and another
request's private instructions or answer must stay separate. Published capstone
tests use public text or made-up examples.

\par\medskip\noindent\phantomsection\label{req:SR-04}
\textbf{SR-04 --- Keep private instructions and answers separate}\par
Tandem shall prevent another request's private instructions or generated answer from becoming part of the history reused by the current request.\par
\textbf{Fit criterion.} T-ISOLATION changes another request's private instructions while keeping the current request fixed. Score changes meet \hyperref[req:NFR-05]{\texttt{NFR-05}}, greedy output stays the same, and the equivalent check without Tandem also passes.\par
\textbf{Source and rationale.} BR3; addresses risk H2. Permission to share history does not grant access to private later text.



\par\medskip\noindent\phantomsection\label{req:SR-05}
\textbf{SR-05 --- Invalidate old caches after restart or setup changes}\par
The first release shall limit reuse caches to the configured serving lifetime and invalidate their local references after a restart or incompatible configuration change.\par
\textbf{Fit criterion.} T-RESTART checks that an old reference cannot permit reuse in a restarted process or changed setup. Default logs and reports do not save prompts or caches.\par
\textbf{Source and rationale.} BR3; addresses risk H3. Physical GPU-memory erasure remains the host's responsibility.

\subsection{Audit Requirements}
Logs need to explain which request ran, which setup was used, whether a cache
was reused and why a failure occurred. They do not need to store private
conversation text to explain those decisions.

\par\medskip\noindent\phantomsection\label{req:SR-06}
\textbf{SR-06 --- Keep private contents out of normal logs}\par
Normal logs and measurement files shall omit raw prompts, generated answers, cache data, credentials and request-controlled secrets while retaining IDs and status/reason codes.\par
\textbf{Fit criterion.} T-PRIVACY places recognizable test secrets in requests and caches and checks that normal exports contain none. Detailed output traces require explicit operator enablement, public/synthetic test data and a stated storage lifetime.\par
\textbf{Source and rationale.} BR3; addresses risk H5.

\subsection{Immunity Requirements}
Prompt text and generated answers are data, not commands for changing the
server. Tandem does not execute them as code. The host remains responsible
for operating-system, file and network protection.

\par\medskip\noindent\phantomsection\label{req:SR-07}
\textbf{SR-07 --- Check size and format limits}\par
Tandem shall check request sizes and cache descriptions against the supported configuration before using the associated resources.\par
\textbf{Fit criterion.} T-BOUND sends inconsistent lengths, invalid cache references, unsupported formats and oversized requests. Each has a clear rejection, normal-processing or failure outcome, with no unlimited retry loop.\par
\textbf{Source and rationale.} C4, BR2; addresses risks H1, H3 and H6.



\par\medskip\noindent\phantomsection\label{req:SR-08}
\textbf{SR-08 --- Do not mix a failed answer with a restarted answer}\par
Tandem shall never present output from a failed reuse attempt followed by output from a restarted normal run as one successful response.\par
\textbf{Fit criterion.} T-FAIL causes an error after output starts and checks that the final status is failed. A restart before output begins keeps the original request ID without duplicating output.\par
\textbf{Source and rationale.} BR4; addresses risk H7 and \hyperref[req:FR-07]{\texttt{FR-07}}.

\section{Off-the-Shelf Solutions}


\subsection{Ready-Made Products}
The serving engine already loads models, produces responses and can reuse
some shared prompt prefixes~\hyperref[src:APC]{[APC]}. Those existing features
are the starting point and stay enabled in the baseline. The team will first
measure what the chosen engine version already does, then test whether Tandem
adds a useful improvement when the selected model changes.

\subsection{Reusable Components}
The team can reuse existing model loaders, tokenizers, tensor operations,
cache functions and profiling tools. Reusing a library saves implementation
work, but the combined system still needs the required output, privacy and
failure-handling tests.

\subsection{Products That Can Be Copied}
The project will extend existing serving software rather than copy a whole
application. Examples and extension code may be adapted when their licences
allow it, with credit and required notices retained. Results published by
another project provide background; they are not measurements of Tandem.

\section{New Problems}


\subsection{Effects on the Current Environment}
Cache checks, data movement and extra bookkeeping also take time and memory.
They could make some requests slower, especially when no useful history can be
reused. The tests therefore include normal requests as well as requests expected
to benefit from Tandem.

\subsection{Effects on the Installed Systems}
An engine update may break the code that loads reused caches. Each release
must say which versions it supports and provide a way to turn reuse off.
Tests check that the application still uses the same selected model and settings
and that ordinary requests continue to work.

\subsection{Potential User Problems}
Users might assume that any model the engine can load also supports cache
reuse, or think that an unused cache means their request failed. They might
also compare tests where only one run started with a prepared cache. Instructions
and reports must explain these cases. A model can still give a factually wrong
answer even when Tandem produces exactly the same answer as normal processing.

\subsection{Limitations in the Anticipated Implementation Environment That May
Inhibit the New Product}
The GPU may not have enough memory to hold the selected models together.
The engine may not provide an easy way to insert a cache or measure actual
prompt work. Small numeric differences may make exact repeatability difficult.
Preparing and moving a cache may also take longer than reprocessing the history.
Any of these problems can prevent a model setup from passing its tests or
showing a speed benefit, and the report must say when this happens.

\subsection{Follow-Up Problems}
A new model/software version or a discovered output mismatch requires the
affected reuse setup to be disabled and tested again. If the team cannot find
a correct, useful cross-model method, it must review the scope with course
staff. A tool that only measures repeated work could be a revised direction,
but it would not automatically meet this SRS's optimization goals.

\section{Migration to the New Product}


\subsection{Requirements for Migration to the New Product}
An operator first checks that the models run normally with reuse turned off.
They then follow the setup instructions and run the output and compatibility
tests. Reuse is enabled only for a setup that passes. To return to the earlier
behaviour, the operator turns reuse off or restores the recorded unmodified
engine version. The application keeps its existing routing and conversation storage.

\subsection{Data That Has to be Modified or Translated for the New System}
No application database needs to be converted. Existing caches are not
assumed to work across models or software versions. The trusted provider must
prepare a cache in the supported format, and Tandem must check it before use.
References to old caches become invalid after a restart or incompatible
configuration change. Measurement files record their format version so that
analysis tools can detect an incompatible file.

\section{Costs}
Expected costs are development time, GPU time, model storage, test runs and
maintenance when the serving engine changes. The project records do not yet
provide a confirmed money budget or measured savings. Reducing repeated
prefill is intended to reduce serving cost, and the tests must show whether
the saved work outweighs the overhead of preparing and transferring caches.

For each matching workload, report the total time for which each GPU is
allocated to the run, including cache preparation and transfer. Sum that time
across the GPUs used and divide by the number of successfully completed
requests to obtain GPU time per completed request. Failures and their resource
use remain in the totals; they must not make the result look cheaper.
Also report actual prompt work, response delay and throughput so readers can
see what changed.

If GPU rental rates are supplied, estimate serving cost by multiplying each
GPU's allocated hours by its stated hourly rate, adding any other included
charges, and dividing by successful completions. State the rates, billing
assumptions and which costs are included. With no price information, report
resource savings rather than a money figure. On already-owned hardware,
completing more requests with the same GPUs can be a capacity benefit even
when the immediate bill stays the same.

The main comparison keeps routing decisions unchanged to measure Tandem's
contribution. Any additional comparison between a workload using one expensive
model and a workload routed among cheaper models must be reported separately,
with the model choices, prices and task-quality checks stated. Savings due to
model selection must be distinguished from savings due to Tandem's prefill reuse.

\section{User Documentation and Training}


\subsection{User Documentation Requirements}
The repository will contain instructions for installing, using, testing
and troubleshooting Tandem.

\par\medskip\noindent\phantomsection\label{req:DR-01}
\textbf{DR-01 --- Explain installation and operation}\par
The release shall document prerequisites, supported setups, request/response fields, reuse controls, normal processing, error codes, rollback and a repeatable basic example.\par
\textbf{Fit criterion.} T-DOC checks these topics and asks an independent technical reviewer to run the example under \hyperref[req:NFR-02]{\texttt{NFR-02}}. Supported limits and known problems are explicit.\par
\textbf{Source and rationale.} Application developers, operators and maintainers need usable instructions.

\subsection{Training Requirements}
Users do not need a formal training course. A short walkthrough uses public
or made-up text to show a normal request, successful reuse, a cache that cannot
be used, and a processing failure. It explains the results and the next steps
using ordinary command-line tools.

\par\medskip\noindent\phantomsection\label{req:DR-02}
\textbf{DR-02 --- Explain test results}\par
The release shall explain how to repeat and interpret the normal-processing/Tandem comparison, including starting cache conditions, uncertainty, failures and output tolerances.\par
\textbf{Fit criterion.} T-DOC follows a sample report back to its settings and individual results. A failed or inconclusive result must be clearly distinguishable from a passed requirement.\par
\textbf{Source and rationale.} G1--G4; readers need to understand both the results and their limits.

\section{Waiting Room}
Possible later features include more conversation branches, more model
families, more GPU configurations, measured reductions in peak memory, and
support for another serving engine. Reusing differently worded text, running
across several servers, building a router or providing a public application
would require an expanded project scope. These features are not needed to
complete the initial release.

\section{Ideas for Solution}
One possible design is a small integration layer between a trusted KV cache
provider and the LLM serving engine. It validates the cache's target model,
shared token prefix and compatibility metadata, then loads the accepted KV
tensors into the engine's KV memory. The target model prefills the uncached
prompt tokens and continues autoregressive decoding, generating one token at
a time. If reuse is unavailable, the engine falls back to native prefill.

Separate test tools send the same requests to the original engine and the
modified engine and compare their outputs and performance. The team will choose
an existing cache-transfer approach if a suitable one is available; inventing
a new predictor is outside scope. The earlier tree-attention and KV-Promise
ideas in the Development Plan are not required by this version of the SRS.
