\section{Purpose of the Project}


\subsection{User Business}
Tandem develops a predictor that estimates a target large language model's
key-value (KV) cache from a source model's KV cache for the same conversation
prefix. This aims to avoid repeated target-model prefill when a conversation
switches models, reducing GPU compute and time to first token.

In the planned deployment, vLLM Semantic Router selects the target model
\hyperref[src:VSR]{[VSR]}. Tandem checks and loads the prediction, then the
engine prefills the uncached suffix and decodes the response. Unsupported or
failed predictions use native processing. Prediction may be approximate;
KV error, output effects and total serving cost must be measured.

The project includes predictor development, any required fitting/training
and integration on one GPU-equipped server. Base LLM weights remain frozen;
older scope documents require alignment under OI5.


\subsection{Goals of the Project}
Tandem addresses repeated prefill after model switches~\hyperref[src:PS]{[PS]}:
\begin{description}
\item[G1: Predict target KV from source KV.] Develop and integrate a predictor
that lets supported target models reuse the shared history without repeating
prefix prefill.
\item[G2: Reduce compute and serving cost.] Lower GPU time per completed
request after counting prediction, validation and cache-loading overhead.
\item[G3: Support economical model switching.] Preserve the benefit of routing
suitable requests to cheaper models by reducing repeated history processing.
\item[G4: Improve latency and throughput.] Lower time to first token (TTFT)
and increase completed requests per second within the agreed latency limits.
\end{description}
Matched native/Tandem tests measure KV error, output effects, actual prompt
work, GPU time, latency and throughput. Cost claims state rates and assumptions;
router-selection savings are reported separately. Output accuracy, privacy
and native fallback remain required.


\section{Stakeholders}


\subsection{Client}
A potential client is a multi-model application company such as
Cursor~\hyperref[src:CURSOR]{[CURSOR]}, whose team could help identify useful
model combinations, acceptable response delays and cost-saving goals; this
is a proposed adoption scenario, not a confirmed partnership.


\subsection{Customer}
A potential customer is an inference provider such as
Together AI~\hyperref[src:TOGETHER]{[TOGETHER]} or an internal AI infrastructure
team that could deploy Tandem to serve more requests with its GPUs; adoption
of the planned open-source software does not require a licence purchase.


\subsection{Other Stakeholders}
Other people who could benefit include:
\begin{itemize}
\item \textbf{Independent application developers looking to host local LLM:} could provide faster
AI features without needing to build their own serving optimization.
\item \textbf{Inference Data Center Operators:} could make better use of limited GPU capacity
and see clear information about cache reuse and failures.
\item \textbf{Researchers:} could use the test tools and results to study
when sharing cached calculations is useful and when it is ineffective.
\end{itemize}

\subsection{Hands-On Users of the Project}
Engine developers integrate the predictor; operators configure approved
predictors and resource limits; researchers evaluate results; application
developers use the existing serving interface. Technical users need Linux,
LLM-serving and GPU knowledge. vLLM Semantic Router selects the target model,
and application end users need no knowledge of Tandem.

\section{Mandated Constraints}


\subsection{Solution Constraints}
The initial project has these limits:
\begin{description}
\item[C1:] Run text-generation requests on one server.
\item[C2:] Use the target model selected by vLLM Semantic Router, or the same
recorded routing decision when replaying a benchmark.
\item[C3:] Use existing trained source and target LLMs with frozen base-model
weights. Developing a KV cache predictor, including fitting or training its
parameters if the chosen method requires it, is part of Tandem.
\item[C4:] Reuse only an exact matching start of the conversation, using a
model pair and KV prediction method that have passed the required tests.
\item[C5:] Keep the serving engine's normal prompt processing available
whenever reuse is not possible.
\end{description}
These limits keep the project manageable and allow a fair comparison with the
serving engine running without Tandem~\hyperref[src:PS]{[PS]}.

\subsection{Implementation Environment of the Current System}
Use a Linux GPU server with sufficient model memory, with vLLM as the planned
engine and SGLang as an alternative~\hyperref[src:DP]{[DP]}; record exact model,
tokenizer, engine and GPU-software versions before testing. CPU checks do not
establish GPU performance, and the first model pair remains open (OI1--OI2).


\subsection{Partner or Collaborative Applications}
The application sends conversation messages and generation settings through
the existing serving interface. vLLM Semantic Router chooses the target model
\hyperref[src:VSR]{[VSR]}; the engine provides source KV state through an
internal cache reference, rather than an application HTTP tensor payload
\hyperref[src:VLLMAPI]{[VLLMAPI]}.

Tandem predicts target KV state using source keys/values and model-pair,
prefix and alignment metadata, checks the result, loads accepted state and
prefills every token after the covered prefix before decoding. The complete
logical prompt remains available for validation and fallback. Native target
KV references are generated offline for development/evaluation, not as a hidden
shared-prefix prefill step during serving. The application retains conversation
storage and access control; benchmark tools replay identical routing decisions.
The predictor method, fitting procedure and supported pair are open under OI1.


\subsection{Off-the-Shelf Software}
Reuse the serving engine, Python, PyTorch, Hugging Face Transformers,
tokenizers and GPU libraries; record versions/licences and rerun compatibility
tests after relevant updates. Predictor training is in scope; base-LLM training is not.


\subsection{Anticipated Workplace Environment}
Develop locally and use a shared Linux GPU server for model experiments,
recording hardware and competing workloads for repeatable performance tests.


\subsection{Schedule Constraints}
The Development Plan schedules the SRS/Hazard Analysis for October 19, 2026,
proof of concept in November, initial demonstration in February and final
work in March--April; confirm course dates and reconcile scope under OI5
(see Section~\ref{sec:phases}).


\subsection{Budget Constraints}
Use existing university GPU resources; available compute time and storage
remain unconfirmed (OI7), so reschedule or reduce tests if resources are insufficient.


\subsection{Enterprise Constraints}
Review repository changes through issues and pull requests, record release
versions, and keep credentials and private conversations out of public files;
use only public, synthetic or permitted test data.

\toprule Term & Meaning\\\midrule\endhead
LLM & Large language model: a model that can generate text.\\
Inference & Running a trained model to produce an output, rather than training its parameters.\\
Semantic routing & Selecting a target model based on request needs and configured policy. The planned deployment uses vLLM Semantic Router; Tandem uses its selection.\\
Serving engine & Software that loads models, schedules requests and returns their responses.\\
Source/target model & The earlier LLM that produced the predictor's input KV cache, and the selected LLM whose KV cache Tandem predicts.\\
Token/tokenizer & A token is a piece of text, such as a word or part of a word. A tokenizer converts text into these pieces.\\
Prefill & The inference phase that processes the input prompt and computes attention state before response generation.\\
Decoding & The inference phase that generates response tokens one at a time, using and extending the KV cache.\\
Attention & The model mechanism that uses query, key and value tensors to combine information from tokens in the context.\\
Tensor & A multidimensional array of numbers used to store model data and intermediate results.\\
KV cache & Key-value cache: the key and value tensors stored by attention layers for processed tokens, so they need not be calculated again.\\
Source KV cache & Attention state from the previously used model. Its model, covered prefix and token positions are recorded before considering cross-model reuse.\\
Cache handle & A reference used to locate managed KV tensors without placing the tensors themselves in the application request.\\
Uncached prompt suffix & The prompt tokens after the cached prefix. These still require target-model prefill and can include more than the latest user message.\\
KV cache predictor & Tandem's mapping from source-model keys and values to estimated target-model keys and values for the same prefix. Its parameters may be learned or otherwise fitted, depending on the chosen method.\\
Predicted target KV cache & The predictor's estimate of the target model's attention state. It can differ from the native target cache and must be evaluated for accuracy.\\
Native reference KV cache & Target-model KV tensors computed by normal prefill for the same prefix, used as ground truth during predictor development and offline evaluation.\\
Cache provider / loading component & Trusted engine-side software that retrieves source KV state and makes accepted predicted tensors available to the target engine.\\
Cross-model KV reuse & Using target KV state predicted from a source model's KV state to avoid repeating target-prefix prefill. Supported model pairs and predictor versions are tested explicitly.\\
Prefix caching & Reusing a KV cache for an exact shared start of a prompt, avoiding repeated prefill for that prefix.\\
Candidate cache & Predicted target-model KV state being considered for reuse. It must pass the required runtime checks before it is used.\\
Target-ready cache & A cache prepared in the form required by the selected model. This alone does not prove that it is correct.\\
Context prefix & The exact start of the conversation history shared by requests, expressed as tokens for the selected model.\\
Native prefill & The serving engine's standard prompt-processing path when Tandem's cross-model cache reuse is not used. Existing prefix caching can still apply.\\
Native processing / baseline & The serving engine running without Tandem's changes, including its existing cache features. This is the reference for output and performance comparisons.\\
Fallback & Returning to normal processing when Tandem cannot safely use a cache.\\
Compatibility manifest & The supported-setup list: records the model pairs, software versions and cache settings approved through testing.\\
Profile / qualification & A profile describes one model/cache setup. Qualification means checking that setup against the required tests before enabling reuse.\\
Reuse domain & An allowed sharing group, assigned by the host application, that controls which requests may share cached history.\\
Cold/warm cache & A cold cache has no useful saved prefix. A warm cache already contains relevant calculations.\\
TTFT & Time to first token: the wait from receiving a request to returning its first output token.\\
Latency / throughput & Latency is a delay, such as TTFT or end-to-end time from request arrival to completion. Throughput is the number of successfully completed requests per second.\\
p50 / p95 & The median and the 95th-percentile time. At p95, 95\% of the measured requests have a time at or below that value.\\
Logit / greedy generation & A logit is a score the model assigns to a possible next token. Greedy generation chooses the highest-scoring token at each step.\\
Confidence interval & A range used to describe uncertainty in a result across repeated tests.\\
GPU / CPU & Graphics processing unit / central processing unit: processors used to run model calculations and other program work.\\
API & Application programming interface: the way another program sends requests and receives results.\\
V\&V / PoC / Rev 0 & Verification and validation / proof of concept / initial integrated demonstration.\\

request; a model ID includes the model's exact version, not just its display

\section{Relevant Facts And Assumptions}


\subsection{Relevant Facts}
\begin{itemize}
\item \textbf{Fact 1:} Tandem addresses repeated prefill after model switches
by predicting target-model KV state from source-model KV state. The earlier
problem statement describes the model-switching problem; its integration-only
scope needs updating to include predictor development~\hyperref[src:PS]{[PS]}.
\item \textbf{Fact 2:} vLLM already supports reusing previously processed shared prompt prefixes;
this reduces prefill work rather than the work of generating new tokens~\hyperref[src:APC]{[APC]}.
\item \textbf{Fact 3:} A cache must match the intended model, conversation and calculation settings.
Having the same size is not enough to show it can be reused correctly.
\item \textbf{Fact 4:} Repeating model results requires controlled software and hardware settings~\hyperref[src:REPRO]{[REPRO]}.
\end{itemize}

The supplied project files do not yet contain measured Tandem performance or
evidence that a KV predictor meets its accuracy and performance criteria.

\subsection{Business Rules}
BR1: Tandem uses the router-selected target model. In the planned deployment,
vLLM Semantic Router makes that selection; benchmark replay preserves it.
BR2: A valid request can still run normally when no cache can be reused.
BR3: Cached private information is shared only with requests allowed to use it.
BR4: Responses, errors and measurements keep the correct request ID.
BR5: A performance claim includes the test requests, settings and output checks
needed to assess it.
BR6: A predictor/model-pair setup is listed as supported only after its
versioned predictor passes the required offline accuracy, output, privacy
and failure-handling tests.

\subsection{Assumptions}
A1: The server operator controls the model files and settings. The initial
cache provider runs in this trusted environment; users cannot upload arbitrary
cache files directly.
A2: The application supplies the intended conversation history and new turn;
vLLM Semantic Router supplies the target-model selection. Tandem still checks
that the request is well formed and within supported limits.
A3: The available server can run the selected models normally. Tests still cover
what happens when memory runs out.
A4: The team can develop a useful KV predictor for at least one model pair.
Whether prediction can meet the accuracy criteria while taking less work than
target-prefix prefill is a proof-of-concept question, not an established result.
A5: Public or synthetic conversations are available to produce paired source
and native target KV data for predictor development and held-out tests.
A6: The team can control or record other work using the GPU during testing.
If an assumption is wrong, the team will review the affected requirements and
record any change to the test plan.

\subsection{Specifying a Business Use Case (BUC)}
\textbf{BUC1: Answer the next conversation message.} The application has a
new message, and vLLM Semantic Router selects the target model. Tandem uses
the source model's KV cache to predict the target model's KV cache for the
shared prefix. If the prediction passes the runtime checks for an approved
setup, Tandem loads it and prefills only the uncached suffix. Otherwise, the model
processes the prompt normally. The application receives the response under
the same request ID. Invalid inputs are rejected clearly, and a failure during
processing is reported rather than presented as a successful answer.

\textbf{BUC2: Check whether a setup benefits from Tandem.} An operator or
researcher runs a fixed set of requests with and without the changes. The
report compares predicted and native target KV tensors, output consistency,
prediction time, response times, completed requests, resource use and failures.
It states which source/target models, predictor version and settings were tested.

\section{Business Data Model and Data Dictionary}


\subsection{Business Data Model}
A test run links its configuration and requests; each request links its model,
sharing group, source cache, prediction attempt, output events and measurements.
A prediction links a versioned predictor and source/target pair to candidate
KV state with covered-prefix metadata. Accepted requests end once as completed,
failed or cancelled; rejections are separate. Comparisons pair corresponding
native/Tandem requests, while applications retain conversation storage.


\subsection{Data Dictionary}
The fields below describe the logical inference inputs and engine-side cache
state. They do not require the application to send KV tensors in an HTTP
payload. The uncached suffix is derived after validating the cached prefix;
the full prompt remains available for validation and fallback.
\begin{longtable}{@{}p{0.20\textwidth}p{0.25\textwidth}p{0.49\textwidth}@{}}
\toprule Field & Allowed value & Purpose\\\midrule\endhead
\texttt{run\_id} & Nonempty text & Identifies one test run and its records.\\
\texttt{request\_id} & Nonempty text, unique within the run & Connects a request to its output, final status and measurements.\\
\texttt{history} & Messages in their original order & Includes the conversation and system instructions already provided.\\
\texttt{latest\_message} & Text or a message with a role & The new turn, added using the selected model's conversation format.\\

The input and requested output must fit within the selected model's context
limit and the server's configured limits. The output-token limit must be
positive. Unsupported response controls are rejected rather than ignored.
An unusable optional cache normally leads to standard prompt processing;
invalid requests or server failures can still prevent a response. Normal logs
and measurement files do not include the raw conversation or cache contents.

\section{The Scope of the Product}


\subsection{Product Boundary}
Tandem includes source-to-target KV predictor development and fitting,
reference-data preparation, engine integration, cache validation/loading,
request isolation, fallback and evaluation on one server. The application
supplies the prompt and settings; vLLM Semantic Router selects the target.
Only supported predictors and exact shared prefixes are reused, and existing
native prefix caching remains enabled in the baseline.

Base-LLM training, router development, document retrieval, agent coordination,
a graphical application and multi-server execution are outside scope.

\section{Functional Requirements}


\subsection{Functional Requirements}
\label{sec:functional}
Functional requirements state what Tandem must do. For example, it must
predict target-model KV caches from source-model KV caches, load accepted
predictions and use normal processing when prediction cannot be used.
``Shall'' means the behaviour is required. Each numbered requirement has a
\emph{fit criterion}, meaning how we will check whether it passes, and a
\emph{source and rationale}, meaning where it comes from and why it is needed.

The short labels below are references used to organize this document. They
are not additional AI techniques or features.
\begin{longtable}{@{}p{0.25\textwidth}p{0.69\textwidth}@{}}
\toprule Label & Meaning\\\midrule\endhead
\texttt{FR-01} & Functional Requirement 1: a required system behaviour.\\
\texttt{NFR-05} & Non-functional Requirement 5: a quality requirement, here concerning model-output consistency.\\
\texttt{SR} / \texttt{DR} & Safety/security requirement / documentation requirement. The number identifies the particular requirement.\\
\texttt{G1}--\texttt{G4} & Project Goals 1--4, listed in Goals of the Project.\\
\texttt{C4} & Solution Constraint 4, listed in Solution Constraints.\\
\texttt{BR1} & Business Rule 1, listed in Business Rules.\\
\texttt{A4} & Assumption 4, listed in Assumptions.\\
\texttt{H1}--\texttt{H7} & Draft hazard/risk labels, explained before the traceability table below.\\
\texttt{T-ADM}, \texttt{T-PRED}, etc. & Proposed test identifiers. Their descriptive names appear in the fit criteria. These labels do not mean that test code exists or that testing has been completed.\\
\bottomrule
\end{longtable}

The AI terms keep their usual meanings: \emph{KV} means key-value,
\emph{LLM} means large language model, and \emph{GPU} means graphics processing
unit. A request \emph{ID} is its unique identifier. \emph{TTFT} means time to
first token. Names such as \texttt{RECOVERY\_LIMIT} identify the draft test
settings in Section~\ref{sec:constants}; they are explained there rather
than treated as new technical concepts.

\par\medskip\noindent\phantomsection\label{req:FR-01}
\textbf{FR-01 --- Check requests before processing}\par
Tandem shall check each request against the Data Dictionary before accepting it.\par
\textbf{Fit criterion.} Request validation test (T-ADM) sends missing fields, unknown models, invalid settings, repeated request IDs and prompts that exceed the limits. Each is rejected with a clear reason before generation begins. A valid request without a cache is accepted.\par
\textbf{Source and rationale.} Business Rule 1, Business Rule 2; a bad request and an unavailable cache are different situations.



\par\medskip\noindent\phantomsection\label{req:FR-02}
\textbf{FR-02 --- Use the requested model and inputs}\par
Tandem shall use the router-selected model version, complete ordered prompt and accepted generation settings.\par
\textbf{Fit criterion.} Model and prompt consistency test (T-SEM) compares the model version, formatted prompt and applied settings with the same request run normally. No history or instruction is left out.\par
\textbf{Source and rationale.} Business Rule 1; an optimization must not change what the application asked the model to do.



\par\medskip\noindent\phantomsection\label{req:FR-03}
\textbf{FR-03 --- Match the shared history exactly}\par
Tandem shall reuse only an exact matching start of the history after formatting and tokenizing it for the selected model.\par
\textbf{Fit criterion.} Conversation-prefix matching test (T-MATCH) changes a message, message order, system instruction, tokenizer or conversation-format version, or token position. Each relevant mismatch prevents that cache from being used. The latest user turn is still processed as new input.\par
\textbf{Source and rationale.} Solution Constraint 4; similar meaning or equal cache sizes do not establish an exact match.



\par\medskip\noindent\phantomsection\label{req:FR-04}
\textbf{FR-04 --- Validate a KV cache before reuse}\par
Tandem shall use a predicted target KV cache only when all predictor-version, compatibility, prefix-matching, permission, readiness and resource checks in Section~\ref{sec:formal} pass, including tensor-shape and finite-value checks.\par
\textbf{Fit criterion.} Cache compatibility test (T-COMP) makes each check fail separately, then tests a valid case. Missing evidence, unsupported predictor versions, invalid shapes or nonfinite predicted values prevent reuse. Runtime checks do not require computing the native target KV cache for comparison.\par
\textbf{Source and rationale.} Project Goal 1, Solution Constraint 4, Business Rule 3, Business Rule 6; the cache must be suitable for this request, not merely available.



\par\medskip\noindent\phantomsection\label{req:FR-05}
\textbf{FR-05 --- Load predicted KV state and prefill the remaining prompt}\par
Tandem shall load an accepted predicted KV cache into the serving engine for the selected target model, prefill the remaining prompt once in its original order, and continue decoding from that state.\par
\textbf{Fit criterion.} Predicted-cache loading test (T-REUSE) checks the cached history, remaining-token positions and measured prompt work for a tested setup. Output checks meet the output-consistency requirement, \hyperref[req:NFR-05]{\texttt{NFR-05}}.\par
\textbf{Source and rationale.} Project Goal 1; the predictor's output must replace shared-prefix prefill in the target engine, not remain only an offline prediction.



\par\medskip\noindent\phantomsection\label{req:FR-06}
\textbf{FR-06 --- Keep normal processing available}\par
Tandem shall use normal model processing when reuse is off, unavailable or unsuitable, while keeping the engine's existing prefix-cache features.\par
\textbf{Fit criterion.} Native-processing fallback test (T-NATIVE) checks same-model requests, requests without shared history, missing caches and unsupported model pairs. They still use the correct model and meet the normal output rules.\par
\textbf{Source and rationale.} Solution Constraint 5, Business Rule 2; a valid request must not fail solely because Tandem cannot speed it up.



\par\medskip\noindent\phantomsection\label{req:FR-07}
\textbf{FR-07 --- Recover from or report a prediction/reuse failure}\par
Tandem shall follow the restart and failure rules in Section~\ref{sec:formal} if KV prediction, validation or loading fails.\par
\textbf{Fit criterion.} Failure-recovery test (T-FAIL) forces predictor exceptions, invalid predicted tensors and cache-loading failures before output, plus execution failures after output begins. Before output, a restart uses valid normal-processing state at most \texttt{RECOVERY\_LIMIT} times. Otherwise, a failure is reported.\par
\textbf{Source and rationale.} Business Rule 2, Business Rule 4; repeated retries or mixing two answers would hide what happened.



\par\medskip\noindent\phantomsection\label{req:FR-08}
\textbf{FR-08 --- Keep output attached to the right request}\par
Tandem shall return output in order with the correct request ID and record exactly one final status for each accepted request.\par
\textbf{Fit criterion.} Request-status and output-order test (T-STATE) runs overlapping requests, cancellations and failures. Output order remains correct, and each accepted request ends as completed, failed or cancelled. Rejected requests have separate records.\par
\textbf{Source and rationale.} Business Rule 4; simultaneous requests and restarts must not duplicate or mix responses.



\par\medskip\noindent\phantomsection\label{req:FR-09}
\textbf{FR-09 --- Release memory when a request ends}\par
Tandem shall release resources held for a completed, failed or cancelled request without removing shared state another active request still needs.\par
\textbf{Fit criterion.} Memory-lifecycle test (T-LIFE) repeats these cases for \texttt{LIFECYCLE\_CYCLES}. No finished request retains its own allocation, and other active requests keep producing correct results. The engine may retain reusable cache data under its normal policy.\par
\textbf{Source and rationale.} Project Goal 2, Project Goal 4; unused request allocations are different from caches intentionally kept for reuse.



\par\medskip\noindent\phantomsection\label{req:FR-10}
\textbf{FR-10 --- Record what happened for each request}\par
Tandem shall record the run and request IDs, source and target models, predictor version, prediction time, final status, reuse decision and reason, other timings, and actual prompt-token work in a structured result.\par
\textbf{Fit criterion.} Measurement-record test (T-METRIC) checks the result format and compares measured counts with a short known prompt. An unavailable measurement is marked missing with a reason rather than replaced by an estimate.\par
\textbf{Source and rationale.} Project Goals 1--4; users need to see both the saved work and the failures.



\par\medskip\noindent\phantomsection\label{req:FR-11}
\textbf{FR-11 --- Use matching requests for comparisons}\par
The test tools shall run the same requests, model choices, arrival times and response settings with and without Tandem.\par
\textbf{Fit criterion.} Matched-workload comparison test (T-EVAL) compares request contents and configuration records. Unexplained differences invalidate the comparison. Existing prefix caching remains enabled whenever it is enabled in the baseline.\par
\textbf{Source and rationale.} Project Goals 1--4, Business Rule 5; weakening the comparison system would give a misleading benefit.



\par\medskip\noindent\phantomsection\label{req:FR-12}
\textbf{FR-12 --- Make comparison results repeatable}\par
The test tools shall report KV prediction-error measurements, prediction time, response times, completed requests per second, prompt work, total allocated GPU time and GPU time per completed request, output differences, fallback results and settings for individual cases and the overall run. Any estimated serving cost shall include its rates and calculation.\par
\textbf{Fit criterion.} Report reproducibility test (T-REPORT) checks the code and library versions, hardware, source/target models, predictor parameters or checkpoint, data splits, seeds, test requests, repetitions, starting cache conditions and failures. It includes prediction, cache validation and loading overhead; offline predictor development costs are reported separately. Cost estimates follow the Costs section. Without a price, report GPU time without claiming money savings.\par
\textbf{Source and rationale.} Project Goals 1--4; a speed result needs enough information to be checked independently.



\par\medskip\noindent\phantomsection\label{req:FR-13}
\textbf{FR-13 --- Control supported cache-reuse setups}\par
Tandem shall check its settings, provide a prediction/reuse on/off control and keep a versioned list of tested source/target model pairs, predictor versions, parameter checkpoints and supported limits.\par
\textbf{Fit criterion.} Configuration validation test (T-CONFIG) rejects inconsistent settings, uses normal processing for untested combinations, and prevents incompatible old caches from being used after a model or configuration change.\par
\textbf{Source and rationale.} Solution Constraint 4, Solution Constraint 5; loading a model successfully does not show that cache reuse works for it.



\par\medskip\noindent\phantomsection\label{req:FR-14}
\textbf{FR-14 --- Test a setup before enabling reuse}\par
The test tools shall keep KV prediction-error measurements and passing output, privacy and failure-handling results for each predictor/model-pair setup enabled for cross-model reuse.\par
\textbf{Fit criterion.} Supported-setup approval test (T-QUAL) tries to enable a setup with missing or failed evidence; reuse stays off. The record includes held-out evaluation, predictor and parameter versions, any training-data split, and tested limits. Predictor fitting and final evaluation use separate conversation groups when fitting is required.\par
\textbf{Source and rationale.} Solution Constraint 4, Business Rule 6, Assumption 4; prediction accuracy and downstream output checks must be evaluated before accepting a speed benefit.



\par\medskip\noindent\phantomsection\label{req:FR-15}
\textbf{FR-15 --- Stop cancelled or timed-out requests}\par
Tandem shall accept cancellation and enforce the configured time limit for an accepted request.\par
\textbf{Fit criterion.} Cancellation and timeout test (T-CANCEL) stops queued and running requests and lets a request exceed \texttt{REQUEST\_TIMEOUT}. Each ends with the right reason at a point the engine can safely stop, and releases resources under \hyperref[req:FR-09]{\texttt{FR-09}}.\par
\textbf{Source and rationale.} Project Goal 2, Project Goal 4; an ongoing GPU operation may need to reach a safe stopping point first.


\par\medskip\noindent\phantomsection\label{req:FR-16}
\textbf{FR-16 --- Predict target-model KV caches from source-model KV caches}\par
For each supported model pair and predictor version, Tandem shall estimate
the target model's key and value tensors for a declared conversation prefix
from the source model's KV tensors and recorded alignment metadata. The
prediction path shall not construct those estimates by running native target
prefill over the same shared prefix.\par
\textbf{Fit criterion.} Target-KV prediction test (T-PRED) runs the predictor on evaluation conversations that were not used to fit it,
checks the covered prefix, tensor layout and model-pair metadata, and reports
key/value error against offline native target KV references for each declared
layer or cache group. Instrumentation confirms that shared-prefix target
prefill is skipped on the successful prediction path. The resulting cache is
tested through \hyperref[req:FR-05]{\texttt{FR-05}} and
\hyperref[req:NFR-05]{\texttt{NFR-05}}. Prediction architecture, parameter
versions and any fitting procedure are recorded.\par
\textbf{Source and rationale.} Project Goal 1, Project Goal 2; predicting the target attention state
from the source attention state is Tandem's central function.

\par\medskip\noindent\textbf{Formal specification of KV prediction, cache reuse and failure behaviour.}
\label{sec:formal}
These equations define prediction, reuse eligibility, fallback and output
checks; their variables are defined below and do not prescribe implementation.

For a source model $s$, target model $t$ and shared history $H$, define
\[
 C_s(H)=(K_s(H),V_s(H)),\qquad
 \widehat C_t(H)=f_\theta(C_s(H),s,t,a).
\]
$f_\theta$ predicts target keys/values using versioned parameters $\theta$
and token/layer/head/layout alignment $a$. Predictor fitting may be required;
base LLM weights remain frozen, and architecture is open.

Offline evaluation computes $C_t(H)$ through normal target prefill as the
reference. For each declared layer or cache group, report absolute tensor
error and relative Frobenius error, separately for keys and values:
\[
 e_X=\frac{\|\widehat X-X\|_F}{\|X\|_F},\qquad X\in\{K_t,V_t\}.
\]
If the reference norm is zero, report absolute error and mark relative error
undefined. Native reference caches are for predictor development and testing;
they are not required to construct predictions during a serving request.
Tensor error is reported alongside the output checks in
\hyperref[req:NFR-05]{\texttt{NFR-05}}. Small tensor error alone does not prove
that generated text meets those checks.

In the equations, $r$ is a request, $c$ is a possible cache, $C$ is the set
of predicted candidate caches, and $M$ is the list of tested predictor/model-pair
setups. $m(r)$ is the chosen model version and $d(r)$ is
the request's allowed sharing group. $P(r)$ is the complete prompt after the
chosen model's formatting and tokenization. $H(r)$ is its history portion,
without the new turn. $T(c)$ is the target-model token sequence represented
by the predicted cache, and $n(c)=|T(c)|$ is its length; $K_s$ and $K_t$
above refer to key tensors, not token sequences. A tested setup records the model versions,
predictor and parameter versions, alignment rules, tokenizer, conversation format, positions, numeric precision,
cache format and engine settings required by
\hyperref[req:FR-14]{\texttt{FR-14}}.

Each check below is either true or false. Missing information makes the check
false, so incomplete information cannot permit reuse.
\begin{description}
\item[$V(r)$:] The request has valid inputs and fits the selected model's limits.
\item[$Q(c,r)$:] The predictor/model-pair setup is in the tested list $M$, and this
request falls within the limits covered by those tests.
\item[$I(c,r)$:] The cache covers a nonempty start of the history:
$0<n(c)\leq |H(r)|$ and $T(c)=P(r)[1:n(c)]$. Its target-model formatting,
tokenizer and token positions match. The supported alignment establishes
that the source cache represents the same logical conversation prefix;
source and target token IDs need not be identical unless the method requires it.
\item[$A(c,r)$:] The application permits this request to use the cached
history. Another request's private instructions or answer are not included.
\item[$D(c)$:] The predicted cache is complete, ready, has the required tensor
layout and finite values, and belongs to the current predictor/configuration
version. Its supported profile has passed offline qualification.
\item[$B(c,r)$:] Enough usable resources can be reserved without changing
cache data that another active request still needs.
\end{description}
\[
 E(c,r) \equiv V(r)\land Q(c,r)\land I(c,r)\land A(c,r)\land D(c)\land B(c,r).
\]
All checks must pass; $u$ means prediction/reuse is enabled:
\[
\operatorname{path}(r)=
\begin{cases}
\text{reject}, & \neg V(r),\\
\text{reuse }c, & V(r)\land u\land\exists c\in C:E(c,r),\\
\text{normal processing}, & V(r)\land(\neg u\lor\neg\exists c\in C:E(c,r)).
\end{cases}
\]
Reject invalid requests; use an eligible cache when enabled; otherwise use
native processing. Every selected candidate must pass all checks.

The cache covers $P(r)[1:n(c)]$. The model processes the remaining prompt,
$P(r)[n(c)+1:|P(r)|]$, in order. No prompt token is skipped or logically
processed twice. Matching cache sizes without the model and history checks
is not enough.

After a request is accepted, it is prepared, generates output and ends. If reuse
fails before any output is returned, Tandem may restart normal processing at
most \texttt{RECOVERY\_LIMIT} times. If a safe restart is not possible, report
failure. If output has already started, report failure without appending a new
answer. Cancellation or timeout also ends the request with the correct reason.
Each accepted request has exactly one final status:
\[
 \operatorname{terminal}(r)\in\{\text{completed},\text{failed},\text{cancelled}\}.
\]

For output checks, $z_T$ and $z_B$ are corresponding scores from the same
selected model with and without Tandem. Both runs are given the same tokens
up to the point being compared. For every finite score $j$, require
\[
 |z_{T,j}-z_{B,j}|\leq\varepsilon_{\mathrm{abs}}
                 +\varepsilon_{\mathrm{rel}}|z_{B,j}|.
\]
Here $\varepsilon_{\mathrm{abs}}=\texttt{SCORE\_ATOL}$ and
$\varepsilon_{\mathrm{rel}}=\texttt{SCORE\_RTOL}$. The first is a fixed small
allowance; the second allows a difference proportional to the reference score.
Unexpected nonfinite values, such as an invalid number, fail the test. Any
normal token-masking rules must be applied consistently before comparison.

Greedy generation must also produce the same token sequence, written
$Y_T=Y_B$, for the specified test length or until both runs stop earlier.
Setting the same random seed does not by itself guarantee that every sampled
answer will match~\hyperref[src:REPRO]{[REPRO]}. Sampling settings need their
own recorded checks before a setup is supported; otherwise the request uses
normal processing.

First, repeat the model run without Tandem to check that the chosen setup is
stable enough for this comparison. Then compare runs with and without reuse.
Passing the tests supports the tested requests and settings; it is not a
mathematical proof that every possible prompt will behave identically.

\section{Performance Requirements}


\subsection{Speed and Latency Requirements}
\label{sec:performance}
Measure TTFT, end-to-end latency and throughput on preselected workloads,
including non-reuse cases. Timing includes queueing, source retrieval,
prediction, checks/loading, suffix prefill and decoding; handle model loading
consistently. Separate predictor/loading/engine timings and offline development
costs, and retain failures and cancellations.

For native baseline $B$ and Tandem $T$, $L$ is median TTFT, $P$ is p95 TTFT
and $Q$ is successful requests per second:
\[
 S_L=L_B/L_T,\qquad S_Q=Q_T/Q_B.
\]
Values above one indicate improvement. T-STAT resamples complete paired
trials using \texttt{CONFIDENCE} and \texttt{BOOTSTRAP\_DRAWS}; requests
within a trial are not independent repetitions.

\par\medskip\noindent\phantomsection\label{req:NFR-04}
\textbf{NFR-04 --- Show a useful reduction in waiting time}\par
On at least one model-switch test chosen in advance, the tested integration shall reduce repeated prompt work and improve median first-token waiting time beyond normal timing variation.\par
\textbf{Fit criterion.} T-PERF requires fewer actually computed prompt tokens and a lower confidence bound for $S_L$ above one. Output checks pass and failures do not increase. Results for other tests, including slowdowns, are reported.\par
\textbf{Source and rationale.} G1, G2, G4; the project must demonstrate a measured benefit rather than assume a fixed speedup.

\subsection{Safety-Critical Requirements}
\textbf{Not Applicable.} Tandem does not control safety-critical equipment;
software, privacy and resource risks remain subject to the Hazard Analysis.


\subsection{Precision or Accuracy Requirements}
Measure KV tensor error under \hyperref[req:FR-16]{\texttt{FR-16}} and
compare native/Tandem outputs at identical token positions with matched model
and calculation settings. The strict draft score/greedy-token limits need
feasibility review on development data (OI3) before final tests; runtime
compatibility checks cannot prove prediction accuracy. Output consistency
does not establish factual correctness.

\par\medskip\noindent\phantomsection\label{req:NFR-05}
\textbf{NFR-05 --- Keep the selected model's output consistent}\par
Each supported cache-reuse setup shall meet the score-difference and generated-token checks in Section~\ref{sec:formal} for its declared test set.\par
\textbf{Fit criterion.} T-SCORE checks corresponding scores using \texttt{SCORE\_ATOL} and \texttt{SCORE\_RTOL}. T-GEN requires the same greedy tokens for \texttt{CHECK\_TOKENS}, or until both runs stop earlier. A mismatch prevents approval; limits cannot be changed afterwards just to pass.\par
\textbf{Source and rationale.} BR1, BR6; the listed tolerances are proposed values the team still needs to review.

\par\medskip\noindent\phantomsection\label{req:NFR-03}
\textbf{NFR-03 --- Preserve supported text}\par
Tandem shall preserve valid Unicode input through the selected model's normal conversation formatting and tokenization.\par
\textbf{Fit criterion.} T-TEXT checks accented characters, non-Latin scripts, whitespace and delimiters. The prompt tokens match normal processing, with no extra text changes introduced by Tandem.\par
\textbf{Source and rationale.} C4; text differences must not lead to false history matches.


\subsection{Robustness or Fault-Tolerance Requirements}
A failed optional prediction uses native processing when possible; unavailable models or exhausted resources produce an explicit failure.

\par\medskip\noindent\phantomsection\label{req:NFR-06}
\textbf{NFR-06 --- Report failures and allow later normal requests}\par
Tandem shall explain why an accepted request failed and keep normal processing usable after a recoverable cache failure.\par
\textbf{Fit criterion.} T-FAIL supplies incomplete caches, mismatched details, memory-allocation failures and timeouts. Results follow \hyperref[req:FR-07]{\texttt{FR-07}}. If the engine remains healthy, a later valid request can still finish normally. An engine that cannot recover requires operator attention.\par
\textbf{Source and rationale.} C5, BR2; recovery depends on having a working engine and enough resources.

\subsection{Capacity Requirements}
Publish and test the supported prompt lengths, concurrency and memory limits for each model/hardware setup.

\par\medskip\noindent\phantomsection\label{req:NFR-07}
\textbf{NFR-07 --- Handle more requests without excessive delay}\par
On at least one shared-history test chosen in advance, Tandem shall improve completed requests per second beyond timing variation while staying within the allowed p95 delay increase.\par
\textbf{Fit criterion.} T-LOAD requires a lower confidence bound for $S_Q$ above one and an upper bound for $P_T/P_B$ no greater than $1+\texttt{REGRESSION\_LIMIT}$, with no extra failed requests. The requests and arrival times are reported.\par
\textbf{Source and rationale.} G2, G4; serving more requests is not useful if the longer waits become unacceptable.



\par\medskip\noindent\phantomsection\label{req:NFR-08}
\textbf{NFR-08 --- Limit slowdowns for normal requests}\par
For tests that do not need Tandem's cache reuse, the integration shall stay within the allowed changes to response time and throughput.\par
\textbf{Fit criterion.} T-NATIVE-PERF requires upper bounds for $L_T/L_B$ and $P_T/P_B$ at most $1+\texttt{REGRESSION\_LIMIT}$ and a lower bound for $Q_T/Q_B$ at least $1-\texttt{REGRESSION\_LIMIT}$. If the uncertainty is too large, the result is inconclusive, not a pass.\par
\textbf{Source and rationale.} G4, C5; the extra checks and bookkeeping must not cause excessive overhead.

\subsection{Scalability or Extensibility Requirements}
The initial scope is one server and tested model pairs; extra GPUs, model families, conversation branches and multi-server scaling require further qualification or expanded scope.

\par\medskip\noindent\phantomsection\label{req:NFR-09}
\textbf{NFR-09 --- Publish supported models and limits}\par
Each release shall list the model/cache setups that passed testing, their simultaneous-request and token limits, and unsupported settings.\par
\textbf{Fit criterion.} T-QUAL checks supported limit values and values just beyond them. Each support claim has test results. Untested setups remain experimental or have reuse disabled.\par
\textbf{Source and rationale.} C4, BR6; users need to know what has actually been checked.

\subsection{Longevity Requirements}
Maintain the prototype through the final capstone release, retain versioned
code/test records, and qualify model or dependency updates before claiming support.

\par\medskip\noindent\textbf{Likely and unlikely changes.}

LC3: Test requests and available hardware may change; test records should make
those differences clear.
LC4: The team may revise proposed test limits before approving the final plan;
values and reasons belong in the settings table.

UC1: Training base models and choosing the model for a request are expected to
remain outside Tandem.
UC2: The initial version is expected to remain a single-server project.
UC3: Reuse is expected to require exact text-token matches and sharing permission,
rather than accepting text merely because it has a similar meaning.

\section{Security Requirements}


\subsection{Access Requirements}
\label{sec:security}
The first version works within a server environment controlled by its
operator. The application and cache provider are trusted parts of that setup.
The host is responsible for accounts and network access; Tandem still checks
whether the current request is allowed to use the proposed cached history.

\par\medskip\noindent\phantomsection\label{req:SR-01}
\textbf{SR-01 --- Allow only permitted history sharing}\par
Tandem shall reuse cached history only when the host application permits the current request to use it.\par
\textbf{Fit criterion.} T-ISOLATION sends matching histories under different sharing groups and tries to change permission through request-controlled data. Unauthorized caches are neither used nor exposed.\par
\textbf{Source and rationale.} BR3; addresses risk H2.

\subsection{Integrity Requirements}
Before using a cache, Tandem needs to know that it is complete, matches the
current settings and belongs to a model/cache setup that has passed its tests.
Finding a cache in memory is not enough.

\par\medskip\noindent\phantomsection\label{req:SR-02}
\textbf{SR-02 --- Do not use incomplete or incompatible caches}\par
Tandem shall not reuse a cache that is incomplete, has inconsistent details, belongs to an outdated setup, has an unsupported source, or failed the required tests.\par
\textbf{Fit criterion.} T-COMP changes each condition separately. The request uses normal processing or receives a clear server/resource failure; the rejected cache never enters generation. Missing test evidence counts as unsupported.\par
\textbf{Source and rationale.} C4, BR6; addresses risks H1 and H3.



\par\medskip\noindent\phantomsection\label{req:SR-03}
\textbf{SR-03 --- Protect caches still in use}\par
Tandem shall prevent a cache needed by an active request from being removed, changed or reassigned in a way that invalidates that request.\par
\textbf{Fit criterion.} T-LIFE overlaps generation, cancellation and cache replacement/removal. Active output meets \hyperref[req:NFR-05]{\texttt{NFR-05}}, and finished requests release resources under \hyperref[req:FR-09]{\texttt{FR-09}}.\par
\textbf{Source and rationale.} G2, G4; addresses risk H4.

\subsection{Privacy Requirements}
Conversation history and the calculations derived from it can contain private
information. A request may use shared history only when permitted, and another
request's private instructions or answer must stay separate. Published capstone
tests use public text or made-up examples.

\par\medskip\noindent\phantomsection\label{req:SR-04}
\textbf{SR-04 --- Keep private instructions and answers separate}\par
Tandem shall prevent another request's private instructions or generated answer from becoming part of the history reused by the current request.\par
\textbf{Fit criterion.} T-ISOLATION changes another request's private instructions while keeping the current request fixed. Score changes meet \hyperref[req:NFR-05]{\texttt{NFR-05}}, greedy output stays the same, and the equivalent check without Tandem also passes.\par
\textbf{Source and rationale.} BR3; addresses risk H2. Permission to share history does not grant access to private later text.



\par\medskip\noindent\phantomsection\label{req:SR-05}
\textbf{SR-05 --- Invalidate old caches after restart or setup changes}\par
The first release shall limit reuse caches to the configured serving lifetime and invalidate their local references after a restart or incompatible configuration change.\par
\textbf{Fit criterion.} T-RESTART checks that an old reference cannot permit reuse in a restarted process or changed setup. Default logs and reports do not save prompts or caches.\par
\textbf{Source and rationale.} BR3; addresses risk H3. Physical GPU-memory erasure remains the host's responsibility.

\subsection{Audit Requirements}
Logs need to explain which request ran, which setup was used, whether a cache
was reused and why a failure occurred. They do not need to store private
conversation text to explain those decisions.

\par\medskip\noindent\phantomsection\label{req:SR-06}
\textbf{SR-06 --- Keep private contents out of normal logs}\par
Normal logs and measurement files shall omit raw prompts, generated answers, cache data, credentials and request-controlled secrets while retaining IDs and status/reason codes.\par
\textbf{Fit criterion.} T-PRIVACY places recognizable test secrets in requests and caches and checks that normal exports contain none. Detailed output traces require explicit operator enablement, public/synthetic test data and a stated storage lifetime.\par
\textbf{Source and rationale.} BR3; addresses risk H5.

\subsection{Immunity Requirements}
Prompt text and generated answers are data, not commands for changing the
server. Tandem does not execute them as code. The host remains responsible
for operating-system, file and network protection.

\par\medskip\noindent\phantomsection\label{req:SR-07}
\textbf{SR-07 --- Check size and format limits}\par
Tandem shall check request sizes and cache descriptions against the supported configuration before using the associated resources.\par
\textbf{Fit criterion.} T-BOUND sends inconsistent lengths, invalid cache references, unsupported formats and oversized requests. Each has a clear rejection, normal-processing or failure outcome, with no unlimited retry loop.\par
\textbf{Source and rationale.} C4, BR2; addresses risks H1, H3 and H6.



\par\medskip\noindent\phantomsection\label{req:SR-08}
\textbf{SR-08 --- Do not mix a failed answer with a restarted answer}\par
Tandem shall never present output from a failed reuse attempt followed by output from a restarted normal run as one successful response.\par
\textbf{Fit criterion.} T-FAIL causes an error after output starts and checks that the final status is failed. A restart before output begins keeps the original request ID without duplicating output.\par
\textbf{Source and rationale.} BR4; addresses risk H7 and \hyperref[req:FR-07]{\texttt{FR-07}}.

\section{Appendix --- Reflection}

The following are draft document-level observations and a proposed learning
plan. They require team review; individual experiences and course histories
are not asserted on members' behalf.

\begin{enumerate}
\item What went well while writing this deliverable?
\par
The problem statement gave a clear starting point: what Tandem receives, what
it returns and the scope of the work. Writing each requirement together
with a way to test it helped turn those goals into concrete work. The Volere
sections also encouraged us to consider installation, errors and future updates,
as well as response speed.

\item What pain points did you experience during this deliverable, and how did
  you resolve them?
\par
The Development Plan and problem statement described different versions of the
idea. This draft follows the newer focus on switching between models, and OI5
records the need to update the plan. We also still need to choose a model pair,
check how much normal test results vary, and collect feedback from potential
users. These decisions are listed as open issues instead of being treated as settled.

\item How many of your requirements were inspired by speaking to your
  client(s) or their proxies (e.g. your peers, stakeholders, potential users)?
\par
The available project records do not give a confirmed count. The current draft
uses the problem statement, development plan and needs of potential user groups.
After speaking with users or representatives, the team should record which
requirements came from their feedback and update this answer.

\item Which of the courses you have taken, or are currently taking, will help
  your team to be successful with your capstone project.
\par
Useful subject areas include requirements engineering, software testing,
operating systems, algorithms, computer architecture and machine learning.
These areas help with writing testable requirements, understanding model
execution, managing resources and measuring results. The team still needs to
add the specific courses members have taken or are currently taking.

\item What knowledge and skills will the team collectively need to acquire to
  successfully complete this capstone project?  Examples of possible knowledge
  to acquire include domain specific knowledge from the domain of your
  application, or software engineering knowledge, mechatronics knowledge or
  computer science knowledge.  Skills may be related to technology, or writing,
  or presentation, or team management, etc.  You should look to identify at
  least one item for each team member.
\par
The team needs to understand transformer key/value tensors, how layers and
attention heads organize a KV cache, and how source and target representations
can be aligned. We need skills in designing a source-to-target KV predictor,
fitting or training it if the selected method requires this, and measuring
prediction error and its effect on model output. Dataset design must keep
training and evaluation conversations separate. We also need to learn serving-engine
integration, GPU scheduling, memory management and recovery from failures.
For evaluation, we need to design fair speed and cost tests that include
predictor overhead and distinguish improvements from normal variation.
Requirements writing, linking requirements to tests, identifying failure
risks and explaining results clearly are also important.
Learning should be shared so that more than one person understands each
critical part of the system.

\item For each of the knowledge areas and skills identified in the previous
  question, what are at least two approaches to acquiring the knowledge or
  mastering the skill?  Of the identified approaches, which will each team
  member pursue, and why did they make this choice?
\par
For serving-engine behaviour, we can read the documentation and code, or run
small experiments that show request and cache activity. Using both connects
the explanation to behaviour we can observe.

For KV prediction, we can study relevant papers and implementation code, or
build small mapping experiments using paired source and target KV caches
from frozen models. We propose combining both: use the literature to choose
a candidate method, then test its assumptions on a small dataset. If the
method is learned, training exercises and supervised experiments provide
two ways to acquire the required fitting skills.

For accuracy checks, we can study numerical comparison and dataset-splitting
methods, or build reference tests that compare predicted KV tensors and
outputs with native target-model processing. The proposed approach combines
reading with controlled experiments on development conversations, followed
by a separate held-out evaluation.

For GPU behaviour, we can follow profiling tutorials or deliberately trigger
limited memory and cancellation cases. The proposed approach uses both to see
where time and memory go and how failures are handled.

For benchmarking, we can repeat an existing published procedure or build a
small synthetic set of requests. We propose starting with a repeatable synthetic
set and then asking whether it represents potential users' needs.

For requirements and hazards, we can study course examples or walk through
concrete success and failure scenarios. Both help identify missing requirements.
The team must confirm the approaches actually chosen and add its experience
before submitting the reflection.

\end{enumerate}
